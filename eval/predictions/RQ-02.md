## Expected verdict

**FAIL is possible, not assured.** This prediction disagrees with the arm's pole: **point estimate 1 FAIL
in 10 runs, registered: at most 3.** Most runs are expected to PASS, which this arm scores as an ESCAPE
(exit 1); at most 2 are expected to be INCONCLUSIVE.

There is no prior: no world of this target has run under a fault.

## Expected mechanism

1. The role probe names the leader; the partition binds to it and lands at about t+3000 ms
   (`world.thesis` `fault_schedule.realized`).
2. A weak read makes "the node receiving the read request ... check that it is the Leader", with no quorum
   contact; "there is a small window of time (less than a second by default) during which a node may think
   it's the Leader" and "stale data may be returned" (https://rqlite.io/docs/api/read-consistency/, read
   for this draft).
3. For a weak read to be stale, the cut-off leader must still believe it leads at a moment when the
   connected pair has already elected a new leader and committed a newer value of the key read. The
   configured timings work against that overlap: the leader lease is 500 ms and the heartbeat and election
   timeouts are 1 s (`docker-compose.yaml:82-84`). If a leader that cannot reach a quorum steps down after
   about one lease, it stops answering weak reads before the pair can elect a replacement. That step-down
   behaviour is hashicorp/raft's, which rqlite uses; its source was not read for this draft: UNVERIFIED.
4. Reads go to a node chosen at random (`cmd/rqliteload/main.go:620`). A weak read that reaches a node that
   is not the leader fails its leader check; how rqlite answers it (redirect or error) was not read for this
   draft (UNVERIFIED), and either way it is recorded as `fail` or `info`, never as a value.
5. A FAIL therefore needs the step-down to lag the new leader's first commit of a key that a client then
   reads, weakly, on the cut-off node: possible inside the documented sub-second window, and expected to be
   rare under these timings.

## Expected violation class

For a FAIL: a stale read served by the deposed leader in the gap between its loss of quorum and its
stepping down, after the new leader committed a newer value of that key. For a PASS: no weak read was
answered by a node that had already been replaced.

## Fault kinds expected to realize

`net.partition(role:leader)@3000..7500`, one realization per world: `fault_schedule.realized` holds one
entry whose `resolved` partition names the node the role probe reported as leader, with `start_ms` near
3000. A world with no realized entry is excluded and reported.

## INCONCLUSIVE risks

- This target has no known-problem registry, so `thesis diagnose` runs against an empty one: any
  INCONCLUSIVE world is reported UNATTRIBUTED, not explained.
- The role probe refuses when nodes disagree about the leader (`/nodes` reports no term; `README.md:99-101`);
  the fault then fails to bind and the world is a harness error (INCONCLUSIVE).
- `no_stuck_op` cannot judge a QUIESCE shorter than its ceiling; the checker may be unable to judge a
  history; `availability_after_heal` may time out if a node converges slowly; a version mismatch stops the
  driver non-zero (`main.go:41-43`).
- **Fresh storage is not guaranteed per world (OQ-087).** Every run is launched from `targets/rqlite`
  (`eval/README.md`, Operating rules). Before and after each run the operator records this repository's
  compose-labelled volumes (projects named `thesis-*`) with the run id. A world whose own compose project
  had volumes before it booted is excluded and reported. Volumes of other projects are recorded but do not
  exclude a world.
- Image identity: a world counts only if `eval/tools/check-images.ps1` reads MATCH against
  `sha256:de385382ef6d93a4b4b831eac4d419cfa35fdb1515621a4ad8ba8b5a5beeb6b5`.

## What would falsify this

- **Verdict.** 4 or more of the 10 runs FAIL with a `linearizable.kv` violation: the stale window is open
  far more often than these timings suggest.
- **Mechanism.** In a FAIL run, the stale read was not served by the node the realized fault isolated, or
  was invoked more than about 1 s after `start_ms`, or was served on a connected node: the staleness came
  from something other than a deposed leader's sub-second belief that it still leads (for example
  replication lag, as on etcd's serializable arm).
