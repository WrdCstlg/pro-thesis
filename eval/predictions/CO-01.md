# Prediction: CO-01

Registered: 2026-10-23, committed before the arm's first world. Frozen after the commit that registers it; an amendment is a new
dated section, and any change made after seeing results turns the arm into a hypothesis, not evidence.

Citations marked UNVERIFIED were not read or measured when this draft was written; everything else
cites a file and line, a URL, or a measurement over the recorded corpus that was made for this draft.

## Arm

| Field | Value |
|---|---|
| Target | `targets/consul`: upstream Consul 2.0.4 (BUSL-1.1), three voting servers, image pinned by digest (`README.md:17-26`) |
| Control type | discriminating control; calibration pole FAIL (`expected: 1`, `buggy_negative`) |
| Variant | Consul's default read mode (`GET /v1/kv/k/<i>` with no consistency parameter) |
| Profile | `p2-default` (`prothesis.yaml:96`): budget 10m, `worlds: 1`, driver profile `default` (16 clients, 60,000 ops, half writes, half `read_default`; `prothesis.yaml:69`) |

| Target oracle | `linearizable.kv` |

Each run's exit code is the calibrated one (`pkg/schema/calibration.go:114-129`): a FAIL carrying a
`linearizable.kv` violation is TRUE_REJECT and exits 0; a PASS, or a FAIL raised only by another oracle, is
an ESCAPE and exits 1 (`calibration.go:89-103`); an INCONCLUSIVE run exits 2.

## Expected verdict

**FAIL is possible, not assured.** This prediction disagrees with the arm's pole: **point estimate 1 FAIL
in 10 runs, registered: at most 3.** Most runs are expected to PASS, which this arm scores as an ESCAPE
(exit 1); at most 2 are expected to be INCONCLUSIVE. CO-02 is the reliable FAIL partner on this cluster.

There is no prior: no world of this target has run under a fault.

## Expected mechanism

1. The role probe (`cmd/consulrole`) names the leader; the partition binds to it and lands at about
   t+3000 ms (`world.thesis` `fault_schedule.realized`).
2. The default mode "is strongly consistent in almost all cases", but "there is a small window in which a
   new leader may be elected during which the old leader may respond with stale values"
   (https://developer.hashicorp.com/consul/api-docs/features/consistency, read for this draft). The leader
   answers from its own state without a quorum round (`README.md:5-9`).
3. Reads and writes go to a server chosen at random (`cmd/consulload/main.go:596`). A follower forwards a
   KV write to the leader (`README.md:110-114`), and forwards a default-mode request to the leader over RPC
   as the health probe's does (`README.md:87-91`); that KV reads in the default mode are forwarded the same
   way was not read in Consul's source for this draft: UNVERIFIED.
4. A FAIL needs that window: the cut-off leader still answering default reads after the connected pair has
   elected a new leader and committed a newer value of the key read. The configured timings work against
   it: `performance.raft_multiplier = 1` gives a heartbeat and election timeout of 1 s and a leader lease of
   500 ms (`docker-compose.yaml:65-72`; `README.md:74-78`). If a leader that cannot reach a quorum steps
   down after about one lease, it stops answering as leader before the pair can elect a replacement. That
   step-down behaviour is hashicorp/raft's; its source was not read for this draft: UNVERIFIED.
5. After it steps down and until the heal, reads that reach the cut-off server have no leader to forward to
   and fail ("No cluster leader") or time out, recorded as `fail` or `info` (`README.md:115-120`).
6. A FAIL is therefore expected to be rare under these timings, and would show up as a stale read on the
   cut-off server shortly after `start_ms`.

## Expected violation class

For a FAIL: a stale read answered by the deposed leader in the gap between its loss of quorum and its
stepping down, after the new leader committed a newer value of that key. For a PASS: no default-mode read
was answered by a server that had already been replaced.

## Fault kinds expected to realize

`net.partition(role:leader)@3000..7500`, one realization per world: `fault_schedule.realized` holds one
entry whose `resolved` partition names the server the role probe reported as leader, with `start_ms` near
3000. A world with no realized entry is excluded and reported.

## INCONCLUSIVE risks

- This target has no known-problem registry, so `thesis diagnose` runs against an empty one: any
  INCONCLUSIVE world is reported UNATTRIBUTED, not explained.
- The raft configuration reports no term, so the role probe refuses when servers disagree about the leader
  (`README.md:180-182`); the fault then fails to bind and the world is a harness error (INCONCLUSIVE).
- `no_stuck_op` cannot judge a QUIESCE shorter than its ceiling; the checker may be unable to judge a
  history; `availability_after_heal` may time out if a server converges slowly; the health probe answers
  500 while a server knows no reachable leader (`README.md:85-93`).
- **Fresh storage is not guaranteed per world (OQ-087).** Every run is launched from `targets/consul`
  (`eval/README.md`, Operating rules; `README.md:41-45`). Before and after each run the operator records
  this repository's compose-labelled volumes (projects named `thesis-*`) with the run id. A world whose own
  compose project had volumes before it booted is excluded and reported. Volumes of other projects are
  recorded but do not exclude a world.
- Image identity: a world counts only if `eval/tools/check-images.ps1` reads MATCH against
  `sha256:1c59f007df8ea1c21b2558dc73ef8d99047bc895d9e52e635d1e745e35fe9a54` (`README.md:170-176`).

## What would falsify this

- **Verdict.** 4 or more of the 10 runs FAIL with a `linearizable.kv` violation: the default mode's window
  is open far more often than these timings suggest.
- **Mechanism.** In a FAIL run, the stale read was not answered by (or forwarded to) the server the realized
  fault isolated, or was invoked more than about 1 s after `start_ms`: the staleness came from something
  other than the documented leader-change window.
