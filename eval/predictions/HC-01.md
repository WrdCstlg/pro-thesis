# Prediction: HC-01

Registered: DRAFT — not registered. Frozen after the commit that registers it; an amendment is a new
dated section, and any change made after seeing results turns the arm into a hypothesis, not evidence.

Citations marked UNVERIFIED were not read or measured when this draft was written; everything else
cites a file and line, a URL, or a measurement over the recorded corpus that was made for this draft.

## Arm

| Field | Value |
|---|---|
| Target | `testdata/kvfixture` (the reference fixture, three Raft nodes, built locally) |
| Control type | harness control; calibration pole FAIL (`expected: 1`, `buggy_negative`) |
| Variant | the planted defect present: no variant pinned, `KV_VARIANT` unset, so compose builds `prothesis/kvfixture:buggy` (`docker-compose.yaml:50,70`) |
| Profile | `p2-linear` (`prothesis.yaml:121`): budget 10m, `worlds: 1`, driver profile `linear` (16 clients, 60,000 ops, half reads, half writes; `prothesis.yaml:74`) |
| Fault schedule | `net.partition(role:leader)@3000..7500` |
| Target oracle | `linearizable.kv` |
| N and seeds | 10 runs, one world each: `thesis run --arm HC-01 --seed s` for s = 1, 2, ..., 10 |

Each run's exit code is the calibrated one (`pkg/schema/calibration.go:114-129`): a FAIL carrying a
`linearizable.kv` violation is TRUE_REJECT and exits 0; a PASS, or a FAIL raised only by another oracle, is
an ESCAPE and exits 1 (`calibration.go:89-103`); an INCONCLUSIVE run exits 2.

## Expected verdict

`linearizable.kv` FAIL in about half the runs: **point estimate 5 of 10, registered range 2 to 8
inclusive.** The other runs are expected to be PASS (ESCAPE, exit 1), about 3 of 10, or INCONCLUSIVE
(exit 2), about 2 of 10. Expected sensitivity for this arm is therefore about 0.5, not 1.

Basis, measured for this draft over the fixture's recorded corpus (`testdata/kvfixture/.prothesis/runs`,
worlds of profile `linear` whose planned schedule is exactly this fault, build read from each world's
node boot log `event=boot ... variant=`): 112 worlds of the buggy build in 67 runs, of which 51 were
`linearizable.kv` violations (46%), 38 PASS and 23 INCONCLUSIVE; every one realized its fault. Those runs
stopped at their first violating world, which leaves violations per world an estimate of the per-world
rate. The corpus predates a change to how the fault phase nests inside the drive phase, so it is a prior,
not pooled data; the CI job that runs this fault on every push asserts only that a 5-world run FAILs
(`.github/workflows/ci.yml:171-173`).

## Expected mechanism

1. The role probe names the leader; the partition binds to it and lands at about t+3000 ms, recorded in
   `world.thesis` `fault_schedule.realized[0]` (`resolved`, `nodes`, `start_ms`, `end_ms`).
2. The partition drops the other nodes' addresses inside the leader's network namespace (as described in
   `targets/redis/README.md:58-60`; the injector, `internal/perturber/faults/iptables.go`, was not read
   for this draft: UNVERIFIED). Host-side clients still reach the cut-off leader on its published client
   port, the condition the fixture's topology is built around (`README.md:102-111`) and one the prior's
   51 stale-read violations could not have happened without.
3. The two connected nodes elect a new leader within the election timeout (600-900 ms,
   `README.md:71-72`) and commit new writes.
4. The cut-off leader holds a 5-second read lease (`internal/raft/lease.go:50`, `README.md:16-36`). The
   lease is renewed only by majority acknowledgements, so it was last renewed just before t+3000 and
   outlives the 4.5-second partition: the window is deterministic (`README.md:42`).
5. The driver sends every operation to a node chosen at random (`cmd/loadgen/main.go:521`) and issues
   900 of every 1000 reads in lease mode (`main.go:170-171, 528-530`; lease is the server default,
   `README.md:128`). About a third of reads reach the cut-off leader, which answers them from state that
   no longer includes the majority's new writes.
6. A stale read of a key the majority has written is a linearizability violation; `linearizable.kv`
   raises it at ASSERT, and the run is FAIL.

The measured 46% per-world rate says step 5 does not always produce a checkable stale read in a world,
although the window itself is deterministic: a stale read needs a client to read, on the cut-off leader,
a key the majority overwrote inside the window. Why the rate is not higher is not established.

## Expected violation class

Consistency: a stale read served by a deposed leader. The witness names a key and the stale read's
op id; its `meta.target` is the node the fault isolated, and the value it returned predates a write
acknowledged by the new leader before the read was invoked.

## Fault kinds expected to realize

`net.partition(role:leader)@3000..7500`, one realization per world: `fault_schedule.realized` holds one
entry whose `resolved` partition names the node the role probe reported as leader at injection, with
`start_ms` near 3000. A world with no realized entry, or whose start is late enough to leave under one
second of partition, is reported and excluded from the counts. All 112 buggy-build worlds of the prior
realized their fault.

## INCONCLUSIVE risks

- About 20% of the prior's worlds were INCONCLUSIVE (23 of 112): the checker could not judge the history
  (10), `no_stuck_op` could not judge a QUIESCE shorter than its ceiling (KP-003), and
  `resource_return_to_baseline` or `no_unbounded_queue` lacked samples (KP-001, KP-002). Each is
  attributed by `thesis diagnose` against `.prothesis/known-problems.yaml`; a world that dies before
  ASSERT is KP-007.
- The role probe may refuse when nodes disagree about the leader; the fault then fails to bind and the
  world is a harness error (INCONCLUSIVE), not a guess.
- **Fresh storage is not guaranteed per world (OQ-087).** Every run is launched from
  `testdata/kvfixture` (`eval/README.md`, Operating rules). Before and after each run the operator records
  this repository's compose-labelled volumes (projects named `thesis-*`) with the run id. A world whose own
  compose project had volumes before it booted is excluded and reported. Volumes of other projects are
  recorded but do not exclude a world: the repository's Docker-backed tests have been measured to leave
  fixture volumes behind, one of them under a project name that repeats across runs.
- Build identity: the fixture is built locally, so there is no upstream digest to pin. A world counts only
  if its `topology_variant` reads `default` and its node boot logs read `variant=buggy`; a stray
  `KV_VARIANT` in the shell would be recorded as the variant (`internal/control/runner.go:735-738`) and
  the world excluded.

## What would falsify this

- **Verdict.** Fewer than 2 or more than 8 of the 10 runs FAIL with a `linearizable.kv` violation. Nine
  or ten would show the per-world rate is well above the prior's; one or none, well below it. A FAIL
  raised only by another oracle counts as an ESCAPE, not a catch.
- **Mechanism.** In a FAIL run, the witness's stale read was not served by the node the realized fault
  isolated, or was invoked outside the partition window (from `start_ms` to the end of the cut-off
  leader's lease, about `start_ms` + 5000), or returned a value no write before the partition produced.
  Any of those means the FAIL came from something other than the deposed leader's lease.
