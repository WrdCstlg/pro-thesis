1, INCONCLUSIVE exits 2.

## Expected verdict

**PASS in 9 of 10 runs (point estimate); registered: at least 7 PASS and no FAIL.** At most 3 runs are
expected to be INCONCLUSIVE (exit 2), each attributed to a known problem.

Basis, measured for this draft over the fixture's recorded corpus (worlds of profile `linear` under exactly
this fault whose node boot logs read `variant=kvfixed`): 27 worlds in 7 runs, 24 PASS, 3 INCONCLUSIVE, 0
violations; `linearizable.kv` judged all 27 `ok`; every one realized its fault. The corpus predates a
change to how the fault phase nests inside the drive phase, so it is a prior, not pooled data. CI asserts a
5-world `linear` run of this build PASSes on every push (`.github/workflows/ci.yml:175-179`).

## Expected mechanism

1. The role probe names the leader; the partition binds to it and lands at about t+3000 ms
   (`world.thesis` `fault_schedule.realized`).
2. The corrected build's read lease is 300 ms (`internal/raft/lease_fixed.go:22`), inside the 600 ms
   minimum election timeout (`README.md:30-46, 71`).
3. The cut-off leader stops renewing its lease with the partition, so the lease expires about 300 ms
   later, before the two connected nodes can elect a new leader. From then on it cannot answer a lease read
   from local state.
4. Reads that reach it are refused or time out and are recorded as `fail` or `info`, which the checker
   does not count as values. No read returns state older than an acknowledged write, so `linearizable.kv`
   finds no violation, and the built-in oracles pass.

How a lease-expired leader answers a lease read (redirect, error or a quorum read) was not read for this
draft: UNVERIFIED. The prediction rests on step 3 alone: no lease read is served after the lease expires.

## Expected violation class

None. A PASS is expected because the lease cannot outlive a leader's ability to know it is still leader:
`LeaseDuration + maxClockDrift < ElectionTimeoutMin` holds for the corrected build (`README.md:30-36`).

## Fault kinds expected to realize

`net.partition(role:leader)@3000..7500`, one realization per world: `fault_schedule.realized` holds one
entry whose `resolved` partition names the node the role probe reported as leader, with `start_ms` near
3000. A world with no realized entry has not exercised the lease and is excluded and reported, never
counted as a PASS.

## INCONCLUSIVE risks

- 3 of the prior's 27 corrected-build worlds were INCONCLUSIVE. Known causes on this fixture: `no_stuck_op`
  cannot judge a QUIESCE shorter than its ceiling (KP-003); `resource_return_to_baseline` or
  `no_unbounded_queue` lack samples (KP-001, KP-002); the checker cannot judge the history (KP-004 shape);
  a world dies before ASSERT (KP-007). `thesis diagnose` attributes each against
  `.prothesis/known-problems.yaml`.
- The role probe may refuse when nodes disagree about the leader; the fault then fails to bind and the
  world is a harness error (INCONCLUSIVE).
- **Fresh storage is not guaranteed per world (OQ-087).** Every run is launched from
  `testdata/kvfixture` (`eval/README.md`, Operating rules). Before and after each run the operator records
  this repository's compose-labelled volumes (projects named `thesis-*`) with the run id. A world whose own
  compose project had volumes before it booted is excluded and reported. Volumes of other projects are
  recorded but do not exclude a world: the repository's Docker-backed tests have been measured to leave
  fixture volumes behind, one of them under a project name that repeats across runs.
- Build identity: the fixture is built locally, so there is no upstream digest to pin. A world counts only
  if its `topology_variant` reads `kvfixed` and its node boot logs read `variant=kvfixed lease_ms=300`.

## What would falsify this

- **Verdict.** Any FAIL (a FALSE_REJECTION), or fewer than 7 PASS runs. A FAIL from `linearizable.kv`
  would mean the corrected lease still lets a deposed leader serve a stale read; a FAIL from another oracle
  would be a false rejection with its own cause, reported as such.
- **Mechanism.** In a PASS run, a read served by the cut-off leader more than 300 ms (plus clock drift)
  after `start_ms` returns a value, in lease mode, while another node already leads a newer term: the
  lease was not the reason for the PASS. In any run, node boot logs reading anything but `lease_ms=300`.
