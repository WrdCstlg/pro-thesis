# Prediction: RQ-03

Registered: 2026-10-23, committed before the arm's first world. Frozen after the commit that registers it; an amendment is a new
dated section, and any change made after seeing results turns the arm into a hypothesis, not evidence.

Citations marked UNVERIFIED were not read or measured when this draft was written; everything else
cites a file and line, a URL, or a measurement over the recorded corpus that was made for this draft.

## Arm

| Field | Value |
|---|---|
| Target | `targets/rqlite`: upstream rqlite 10.5.3, three voting nodes, image pinned by digest (`docker-compose.yaml:44`) |
| Control type | positive control; calibration pole FAIL (`expected: 1`, `buggy_negative`) |
| Variant | reads at `level=none`: the receiving node's local SQLite, no leadership check |
| Profile | `p2-none` (`prothesis.yaml:95`): budget 10m, `worlds: 1`, driver profile `none` (16 clients, 60,000 ops, half writes, half `read_none`; `prothesis.yaml:66`) |
| Fault schedule | `net.partition(role:leader)@3000..7500` |
| Target oracle | `linearizable.kv` |
| N and seeds | 10 runs, one world each: `thesis run --arm RQ-03 --seed s` for s = 1, 2, ..., 10 |

Each run's exit code is the calibrated one (`pkg/schema/calibration.go:114-129`): a FAIL carrying a
`linearizable.kv` violation is TRUE_REJECT and exits 0; a PASS, or a FAIL raised only by another oracle, is
an ESCAPE and exits 1 (`calibration.go:89-103`); an INCONCLUSIVE run exits 2.

## Expected verdict

**FAIL with a `linearizable.kv` violation in 10 of 10 runs (point estimate); registered: at least 8.** At
most 2 runs are expected to be INCONCLUSIVE; none is expected to PASS.

There is no prior on this target. The closest prior is etcd's serializable-read arm, also a local read with
no quorum check: 4 of 4 recorded worlds violated `linearizable.kv` (measured for this draft over
`targets/etcd/.prothesis/runs`).

## Expected mechanism

1. With `level=none`, "the node receiving your read request simply queries its local SQLite database" and
   "does not perform any Leadership or other cluster-contact checks"
   (https://rqlite.io/docs/api/read-consistency/, read for this draft).
2. Reads go to a node chosen at random (`cmd/rqliteload/main.go:620`); writes go to the believed leader
   (`main.go:34-40`). A follower applies a committed write some time after the leader acknowledges it, so a
   read on a follower can return an older value than a write already acknowledged.
3. That replication-lag staleness needs no fault: on etcd's serializable arm the first stale read came 69 ms
   into the drive phase, before the partition, and stale reads were spread over all three members
   (`targets/etcd/README.md:71-76`). It is expected here too, and may well be what the witness shows.
4. In addition, from about t+3000 ms the partition cuts the old leader off. It keeps answering `none` reads
   from its own SQLite, which stops advancing, while the connected pair elects a leader and commits new
   writes: for the rest of the 4.5 s window, every read it answers of a key written by the majority is
   stale.
5. `linearizable.kv` raises a stale read at ASSERT and the run is FAIL.

## Expected violation class

Consistency: a stale read of a key, served by a node whose local state had not applied a write that was
acknowledged before the read was invoked. The witness may sit on any node (replication lag) or on the
partitioned one (the partition); the verdict prediction does not depend on which.

## Fault kinds expected to realize

`net.partition(role:leader)@3000..7500`, one realization per world: `fault_schedule.realized` holds one
entry whose `resolved` partition names the node the role probe reported as leader, with `start_ms` near
3000. A world with no realized entry is excluded and reported: the arm is registered with the fault.

## INCONCLUSIVE risks

- This target has no known-problem registry, so `thesis diagnose` runs against an empty one: any
  INCONCLUSIVE world is reported UNATTRIBUTED, not explained.
- The checker can return INCONCLUSIVE on a history it cannot judge: it did on 10 of the fixture's 112
  recorded buggy-build worlds under this fault (measured for this draft). Its search grows with the
  operations on a key (etcd's serializable arm was decided by a search over 1,345 operations on one key;
  `targets/etcd/README.md:55-59`).
- The role probe refuses when nodes disagree about the leader (`README.md:99-101`); the fault then fails to
  bind and the world is a harness error (INCONCLUSIVE).
- `availability_after_heal` may time out if a node converges slowly; a version mismatch stops the driver
  non-zero (`main.go:41-43`).
- **Fresh storage is not guaranteed per world (OQ-087).** Every run is launched from `targets/rqlite`
  (`eval/README.md`, Operating rules). Before and after each run the operator records this repository's
  compose-labelled volumes (projects named `thesis-*`) with the run id. A world whose own compose project
  had volumes before it booted is excluded and reported. Volumes of other projects are recorded but do not
  exclude a world.
- Image identity: a world counts only if `eval/tools/check-images.ps1` reads MATCH against
  `sha256:de385382ef6d93a4b4b831eac4d419cfa35fdb1515621a4ad8ba8b5a5beeb6b5`.

## What would falsify this

- **Verdict.** Fewer than 8 of the 10 runs FAIL with a `linearizable.kv` violation, or any run PASSes.
- **Mechanism.** The mechanism is registered as two possible sources, so it is scored on where the stale
  reads are: if the first stale read precedes `start_ms`, replication lag produced the FAIL and the
  partition was not needed (recorded as such, as on etcd); if every stale read is on the partitioned node
  inside the window, the partition produced it. A stale read on a node that had applied the write it misses
  (its own earlier read returned that write) falsifies both.
