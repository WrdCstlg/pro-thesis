# Prediction: RE-01

Registered: 2026-10-23, committed before the arm's first world. Frozen after the commit that registers it; an amendment is a new
dated section, and any change made after seeing results turns the arm into a hypothesis, not evidence.

Citations marked UNVERIFIED were not read or measured when this draft was written; everything else
cites a file and line, a URL, or a measurement over the recorded corpus that was made for this draft.

## Arm

| Field | Value |
|---|---|
| Target | `targets/redis`: upstream Redis 8.10.2, one primary and two replicas with asynchronous replication, one Sentinel per node (quorum 2), image pinned by digest (`README.md:3-8, 37-47`) |
| Control type | positive control; calibration pole FAIL (`expected: 1`, `buggy_negative`) |
| Variant | Sentinel failover with asynchronous replication; `min-replicas-to-write` left at its default of 0 (`docker-compose.yaml:56`; `README.md:54-56`) |
| Profile | `p2-failover` (`prothesis.yaml:90`): budget 10m, `worlds: 1`, driver profile `failover` (16 clients, 60,000 ops, half writes, half reads; `prothesis.yaml:65`) |
| Fault schedule | `net.partition(role:leader)@3000..7500` (the leader is the primary the role probe names) |
| Target oracle | `linearizable.kv` |
| N and seeds | 10 runs, one world each: `thesis run --arm RE-01 --seed s` for s = 1, 2, ..., 10 |

Each run's exit code is the calibrated one (`pkg/schema/calibration.go:114-129`): a FAIL carrying a
`linearizable.kv` violation is TRUE_REJECT and exits 0; a PASS, or a FAIL raised only by another oracle, is
an ESCAPE and exits 1 (`calibration.go:89-103`); an INCONCLUSIVE run exits 2.

The workload is single-key `SET` and `GET` (`README.md:216-217`), which the register checker can express:
this arm is scored as a positive control, not as an oracle-discipline arm.

## Expected verdict

**FAIL with a `linearizable.kv` violation in 8 of 10 runs (point estimate); registered: at least 5.** The
rest are expected to PASS (ESCAPE, exit 1) where the failover did not complete inside the partition, or to
be INCONCLUSIVE (at most 2).

**Stated risk, UNVERIFIED: whether a 4.5-second partition completes a failover.** The partition lasts from
t+3000 to t+7500 ms. With `down-after-milliseconds 1000` and `failover-timeout 3000` (`docker-compose.yaml:111-113`,
restated on the lock-covered `driver.cmd`, `prothesis.yaml:62`), a promotion inside that window is plausible
but has not been observed on this target: no world of it has run under a fault. If failovers rarely
complete inside the window, this arm ESCAPEs in most runs and the prediction is falsified.

## Expected mechanism

1. The role probe (`cmd/redisrole`) names the primary (`redis-n1` at boot); the partition binds to it and
   lands at about t+3000 ms (`world.thesis` `fault_schedule.realized`).
2. The partition is iptables rules in `redis-n1`'s network namespace dropping every other node's address,
   so it also cuts off `redis-n1`'s co-located Sentinel; the host-side driver still reaches `redis-n1` and
   its Sentinel through their published ports (`README.md:58-66`).
3. `redis-n1` keeps accepting writes: `min-replicas-to-write` is 0. Redis documents the consequence: "a
   network partition isolated the old master M1 ... clients, like C1, that are in the same partition as the
   old master, may continue to write data to the old master. This data will be lost forever since when the
   partition will heal, the master will be reconfigured as a replica of the new master, discarding its data
   set" (https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/, "Example 2", read for this
   draft).
4. The Sentinels of `redis-n2` and `redis-n3` see the primary unreachable after 1000 ms, reach the quorum of
   2 and promote a replica. That this completes before t+7500 is the UNVERIFIED risk above.
5. The driver finds the primary as a Sentinel-aware client does, asking the Sentinels in order from the last
   one that answered and re-asking after any operation that was not ok, at most every 200 ms; while
   `redis-n1`'s own Sentinel answers first, the driver goes on writing to `redis-n1` and gets `+OK`
   (`README.md:130-141`).
6. After the heal, `redis-n1` is demoted and discards the writes it acknowledged while cut off. A later
   write to it is refused `-READONLY` (recorded `fail`), the driver asks again and moves to the new primary,
   and later reads return values that omit writes acknowledged before they were invoked. If the driver moves
   to the new primary during the partition instead, its reads there omit the writes `redis-n1` acknowledged.
   Either way `linearizable.kv` raises the lost write at ASSERT and the run is FAIL.

## Expected violation class

Consistency: an acknowledged write lost in a failover. The witness is a key whose read, after a write to
`redis-n1` was acknowledged `+OK` during the partition, returns an older value; the lost write's
`meta.target` is `redis-n1` and its `meta.primary` names `redis-n1`.

## Fault kinds expected to realize

`net.partition(role:leader)@3000..7500`, one realization per world: `fault_schedule.realized` holds one
entry whose `resolved` partition names the primary the role probe reported, with `start_ms` near 3000. A
world with no realized entry is excluded and reported. The failover itself is not a fault and leaves no
harness record: the Sentinels' logs are not captured into the bundle (`README.md:176-189`), so whether it
happened is read from the history (`meta.primary`, `meta.sentinel` and `-READONLY` replies on later records).

## INCONCLUSIVE risks

- This target has no known-problem registry, so `thesis diagnose` runs against an empty one: any
  INCONCLUSIVE world is reported UNATTRIBUTED, not explained.
- The driver refuses to start (exit non-zero, no history) unless every Sentinel names the expected primary
  and reports the quorum and timings on `driver.cmd` (`README.md:70-79`); such a world is INCONCLUSIVE.
- The role probe refuses on any disagreement between the nodes' `INFO replication` and the Sentinels; two
  primaries cannot be ranked (`README.md:193-195`). The fault then fails to bind and the world is a harness
  error (INCONCLUSIVE).
- `availability_after_heal` may time out while the demoted primary resynchronises; `no_stuck_op` cannot
  judge a QUIESCE shorter than its ceiling; the checker may be unable to judge a history.
- **Fresh storage is not guaranteed per world (OQ-087).** Every run is launched from `targets/redis`
  (`eval/README.md`, Operating rules; `README.md:98-101`). Before and after each run the operator records
  this repository's compose-labelled volumes (projects named `thesis-*`) with the run id. A world whose own
  compose project had volumes before it booted is excluded and reported. Volumes of other projects are
  recorded but do not exclude a world. The Sentinels start each world from a tmpfs configuration
  (`README.md:48-52`), so their state does not carry over.
- Image identity: a world counts only if `eval/tools/check-images.ps1` reads MATCH against
  `sha256:2c2dff791878316e3b083188be0d578423b24813cdda5de0e80ea4f7b3e6bfd6` (`README.md:209-215`). The
  Sentinels' and health shims' image is not recorded per world (`README.md:176-183`).

## What would falsify this

- **Verdict.** Fewer than 5 of the 10 runs FAIL with a `linearizable.kv` violation.
- **Mechanism.** In a FAIL run, the lost write was not acknowledged by `redis-n1` during the partition, or no
  later record shows another node as primary (`meta.primary`) or a `-READONLY` reply from `redis-n1`: the
  violation did not come from a failover that discarded acknowledged writes. In a PASS run, a record after
  the heal shows another node as primary: the failover happened and the lost-write path was still not seen.
