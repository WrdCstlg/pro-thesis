Each run's exit code is the calibrated one (`pkg/schema/calibration.go:114-129`): PASS is TRUE_PASS and
exits 0, FAIL is a FALSE_REJECTION and exits 1, INCONCLUSIVE exits 2.

## Expected verdict

**PASS in 10 of 10 runs (point estimate); registered: at least 8 PASS and no FAIL.** At most 2 runs are
expected to be INCONCLUSIVE (exit 2).

There is no prior: no world of this target has run under a fault. One fault-free `smoke` world (also
`?consistent` reads) reached ASSERT during onboarding (`README.md:13-15, 155-160`).

## Expected mechanism

1. The role probe (`cmd/consulrole`) names the leader; the partition binds to it and lands at about
   t+3000 ms (`world.thesis` `fault_schedule.realized`).
2. The `consistent` mode "is strongly consistent without caveats"; "It requires that a leader verify with a
   quorum of peers that it is still leader" (https://developer.hashicorp.com/consul/api-docs/features/consistency,
   read for this draft).
3. The cut-off leader cannot reach a quorum, so it cannot answer a `?consistent` read. Reads sent to it fail
   or time out and are recorded as `fail` or `info`, never as a value (`README.md:115-120`).
4. Reads and writes go to a server chosen at random (`cmd/consulload/main.go:596`); on the connected pair,
   once it has elected a leader, `?consistent` reads reflect every acknowledged write.
5. No read returns a value older than a write acknowledged before it was invoked, so `linearizable.kv` finds
   no violation; the built-in oracles (`no_crash`, `no_panic_log`, `availability_after_heal`,
   `no_stuck_op`; `prothesis.yaml:86`) pass when the servers converge after the heal.

## Expected violation class

None. A PASS is expected because a `?consistent` read needs the quorum the cut-off leader does not have.
CO-01 (default) and CO-02 (`?stale`) are the arms that relax it.

## Fault kinds expected to realize

`net.partition(role:leader)@3000..7500`, one realization per world: `fault_schedule.realized` holds one
entry whose `resolved` partition names the server the role probe reported as leader, with `start_ms` near
3000. A world with no realized entry is excluded and reported, never counted as a PASS.

## INCONCLUSIVE risks

- This target has no known-problem registry, so `thesis diagnose` runs against an empty one: any
  INCONCLUSIVE world is reported UNATTRIBUTED, not explained.
- The role probe refuses when servers disagree about the leader (`README.md:180-182`); the fault then fails
  to bind and the world is a harness error (INCONCLUSIVE).
- `no_stuck_op` cannot judge a QUIESCE shorter than its ceiling; the checker may be unable to judge a
  history; `availability_after_heal` may time out if a server converges slowly.
- A write answered "raft apply failed: leadership lost while committing log" is recorded `info` because its
  entry may still commit (`README.md:115-120`); that is correct, not a risk to the verdict, but it widens the
  checker's search.
- **Fresh storage is not guaranteed per world (OQ-087).** Every run is launched from `targets/consul`
  (`eval/README.md`, Operating rules). Before and after each run the operator records this repository's
  compose-labelled volumes (projects named `thesis-*`) with the run id. A world whose own compose project
  had volumes before it booted is excluded and reported. Volumes of other projects are recorded but do not
  exclude a world.
- Image identity: a world counts only if `eval/tools/check-images.ps1` reads MATCH against
  `sha256:1c59f007df8ea1c21b2558dc73ef8d99047bc895d9e52e635d1e745e35fe9a54`.

## What would falsify this

- **Verdict.** Any FAIL (a FALSE_REJECTION), or fewer than 8 PASS runs.
- **Mechanism.** A `?consistent` read answered with a value by the cut-off server inside the partition
  window; or a PASS run in which the partition did not realize on the server the role probe named leader.
