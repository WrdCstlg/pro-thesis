# 04-fixture.verify

## Verdict

**NEEDS-REVISION**

## Spec fidelity

Yes: five substantive drifts, none of them flagged as such by the design, plus one unavoidable conflict it resolves silently instead of escalating.

1. **`kv:*` / `minority(kv)` target semantics, redefined.** Spec §4.2 declares `- id: n1 / service: kv` (three times) and targets them with `node: "kv:*"`; §4.3 defines TARGET as "wildcards (`kv:*`)" and "quorums (`minority(kv)`, `majority(kv)`)". In that config `kv` is an exact service name. The design renames services to `kv-n1/kv-n2/kv-n3` and states: "`kv:*` and `minority(kv)` / `majority(kv)` resolve over nodes whose *service* matches the glob `kv*`. No new schema field; `mesh` is naturally excluded." The token before the colon is silently promoted from an exact service name to a prefix glob, which also changes the meaning of the frozen constraint `"never partition more than minority of kv"`. The underlying conflict is genuine (Compose cannot host three services named `kv`) and Core Rule 4 requires that go to OPEN_QUESTIONS.md, not into a parenthetical.

2. **The lease's time base, versus §5's "local clock".** Spec §5: "When the paused former leader wakes up **before its local clock invalidates the lease**, it serves a stale read to a client." The design implements the deadline in raft ticks ("we express the deadline in raft ticks so the lease shares a time base with the election timeout") and argues in §2.1 that the spec's own reading "would NOT fire". As shown in finding #3, that argument is false for the partition trigger and for any pause under 5 s. This is a deviation from the normatively described mechanism and belongs in DECISIONS.md + OPEN_QUESTIONS.md; the design logs §2.4's timeline contradiction there but not this.

3. **`prothesis.oracle_output/v1` golden artifact is not conformant.** §4.5 fixes the output object as `{"schema": "prothesis.oracle_output/v1", "oracle", "class", "valid_phases", "status", "witness", "explanation"}`. The design's `golden/witness.json` is `{"oracle":"linearizable.kv","class":"consistency","status":"violated","witness":{...},"explanation":"..."}`: `schema` and `valid_phases` are both absent, in the file explicitly designated as the golden target Phase 3's oracle is written against.

4. **History `value` changes type.** §4.4 shows `"value":7`. The design emits, for `f:"txn"`, `"value":[["r","k/3",null],["w","k/7",30000123]]` and omits `key`. The field *name* is preserved (the design says so explicitly) but its type and semantics are not. Defensible as Elle convention; not free under Rule 2.

5. **Additive `meta` object in history records.** `{"meta":{"node":...,"term":...,"read_mode":"lease",...}}` is not in §4.4's schema. Namespacing it is the right instinct and I would accept it, but it should be a DECISIONS.md entry declaring the normative top level closed and `meta` open, so downstream oracles never key off `meta` for anything soundness-critical.

Minor, accepted as reasonable: `proc.pause` implemented as `docker pause` (cgroup freezer) where §4.3 says "(SIGSTOP/SIGCONT)"; the design argues the case well and both are available; needs a DECISIONS.md line. The invented constraint mini-grammar `"never fault role_hint:proxy"` alongside §4.2's prose constraints (`"never partition more than minority of kv"`) is a new DSL smuggled in as data; harmless now, but it will force a parser design in Phase 2.

Correctly preserved and worth noting: `driver.cmd` verbatim; the frozen `profiles`/`budget`/`allow`/`deny`/`artifacts` shapes; exit code 2 for an unreachable daemon; all six built-in oracles listed per CRUCIBLE §B; `suspect.files` paths matching §4.6's `internal/raft/lease.go` and `internal/kv/read_path.go`; and §2.4's catch that the spec's own causal timeline is impossible on n=3 is correct; freezing n2 and isolating n3 leaves n1 alone, so `9010 n1 elected leader term 5` cannot occur. That belongs in OPEN_QUESTIONS.md, and the design says it will go there.

## Confirmed problems (15)

### P1 [high] `leaseView` is only published inside the leader/heartbeat branch of `onTick()`, so it is never republished after step-down, and the design elevates this to a deliberate "amplifier".

**Why it breaks:** The sketch is:
```
case RoleLeader:
  if r.heartbeatElapsed >= r.cfg.HeartbeatTicks { ...; r.publishLeaseView() }
default:
  r.electionElapsed++ ...
```
Nothing in the `default:` (follower/candidate) branch, and nothing in `becomeFollower`, publishes. After n2 steps down to term 5 at ~16100, `s.leaseView.Load()` still returns `{Role: Leader, Term: 4, LeaseHeld: true}` **forever**, so `read_path.go` keeps taking the `GetLocal` fast path. §2.3's row "~16200 leaseView republished {Follower, held:false}; reads to n2 now 503 NOT_LEADER" cannot happen as coded. This breaks HEAL/convergence verification, breaks the `availability_after_heal` and `no_stuck_op` premises, and makes provebug step 11 ("poll until all three agree") pass on `/status` while `/kv` still lies.
Worse, even with publish-on-transition added, the design *keeps* the once-per-heartbeat cadence as an intentional 50–100 ms stale-role window. That is a **second, independent consistency defect**: a node that has stepped down serves a local read from a published-but-wrong role view. It is present in the `kvfixed` build too, because `lease_fixed.go` only changes `leaseHeld()`, not the publish cadence. So `provebug --expect-clean` can still observe a stale read, and Phase 5's DoD ("`thesis regress` passes once the lease bug in `testdata/kvfixture` is patched") and Phase 6's agentic-repair DoD are both built on a fixture that still violates linearizability after the advertised one-line fix. It also destroys the design's own central justification for hand-rolling Raft: "the one artifact whose entire purpose is to have exactly one known defect."

**Fix:** Publish `leaseView` unconditionally at the end of every `onTick()` and at the end of every state transition (`becomeFollower`, `becomeCandidate`, `becomeLeader`, and on `commitIndex` advance). Role and term in the view must be exact; the only field allowed to be stale is `LeaseHeld`, and even that should be recomputed on load rather than cached, so the *only* defect in the tree is the tick-vs-time comparison in `lease.go`. Drop amplifier (1) entirely; if the Phase 2 DoD schedule then flakes, that is a spec finding for OPEN_QUESTIONS.md, not a reason to add a second bug to the SUT (CRUCIBLE §E: "never make the gate weaker to make it pass"; tuning the system under test to make the tool look good is the mirror image of the same offence).

### P2 [high] `KV_SEED: "${KV_SEED:-1}"` / `:-2` / `:-3` gives all three nodes the *same* seed the moment anything sets `KV_SEED` in the environment.

**Why it breaks:** Compose `${KV_SEED:-N}` only uses `N` when the host variable is unset. The defaults differ per node, but a single host-level `KV_SEED=42` (which is exactly what PRO-THESIS will do to vary worlds from Phase 1 onward, and what I2 requires (`(seed, topology_variant, driver_profile, fault_schedule, phase_timings)`)) collapses all three to 42. All three nodes then derive an identical randomized election timeout from an identical PCG stream and boot within milliseconds of each other, so the first election is a guaranteed three-way split vote, and each retry redraws the *same* value on all three. The cluster can fail to elect a leader at all, or take many rounds. Symptom: `thesis up` health/steady-state flakes, worlds go INCONCLUSIVE, and it looks like a harness bug rather than a fixture bug. This lands precisely when seed variation starts, i.e. after Phase 0 has been declared done.

**Fix:** Never let the world seed be the node seed directly. Pass one `KV_SEED` and have each node derive its own stream in-process: `nodeSeed = splitmix64(worldSeed) ^ fnv64a(KV_NODE_ID)` (or `rand.NewPCG(worldSeed, fnv64a(nodeID))`). Compose then sets the same `KV_SEED` on all three services and correctness does not depend on compose interpolation defaults. Add a `raft_test.go` case asserting three nodes with the same `KV_SEED` draw three distinct election timeouts.

### P3 [high] §2.1's core claim: "a monotonic-deadline lease would NOT fire"; is false in general, so the entire fragile tick-collapse mechanism is unnecessary, and it is also the design's largest deviation from spec §5's literal wording.

**Why it breaks:** Spec §5 says: "When the paused former leader wakes up **before its local clock invalidates the lease**, it serves a stale read to a client." That sentence describes a *wall/monotonic* lease that simply has not expired yet: i.e. pause < 5 s. The design rejects that reading and substitutes a raft-tick time base solely because the Phase 2 DoD example schedule uses a 6.9 s pause.
But the design's own §2.5 shows a monotonic lease fires identically for the partition trigger: with `Lease=5000ms` and `ElectionTimeoutMin=600ms`, `net.partition(minority(kv))@8000..16000` gives a stale-read window of [~8950, 12950] ≈ 4.0 s; the *same* number §2.5 computes for the tick lease, because during a partition the leader is running and both clocks advance at the same rate. And for `proc.pause`, any pause < 5 s (e.g. §2.5's own "pause ≈ 1.1 s" shrink target) fires under a monotonic lease too. The only case the tick base buys is a pause **longer** than the lease, and that case comes from a schedule the design itself proves is internally impossible on n=3 (§2.4 Case B).
Against that near-zero gain, the tick base makes every downstream Definition of Done rest on: (a) Go runtime periodic-timer internals (`runOneTimer` advancing `t.when += t.period*(1 + -delta/t.period)`, i.e. skipping missed periods) plus a non-blocking `sendTime` on a cap-1 channel; true in Go 1.22, but the channel becomes *unbuffered* under Go 1.23+ `asynctimerchan=0` semantics, so the design's stated mechanism ("channel buffer is 1") is already version-specific; (b) cgroup-freezer behaviour in Docker Desktop's VM; and (c) nobody ever refactoring the tick loop. The design's own risk list says the bug "silently vanishes" if (c) happens.

**Fix:** Make the injected defect the **duration violation only**: keep `leaseHeld()` on `r.clock.Monotonic()` with a 5 s lease and no CheckQuorum, so the defect is exactly "`LeaseDuration + maxDrift >= ElectionTimeoutMin` (5000 ms vs 600 ms)" and the fix in `lease_fixed.go` is `300 * time.Millisecond`. This is spec-faithful to §5's "local clock", fires on `net.partition(minority)` with the same 4.0 s window, fires on any `proc.pause` shorter than 5 s, and depends on nothing about Go's timer implementation. Set the canonical schedule's pause to ~3 s (well inside the lease) rather than 5.8 s. If you keep the tick base anyway, it must be a documented DECISIONS.md deviation from §5's wording plus an OPEN_QUESTIONS.md entry, not presented as the obvious reading.

### P4 [high] `driver.profiles` (`clients`, `ops`, `mix`) never reach the loadgen, because the normative `driver.cmd` template only interpolates `{history_path}`, `{seed}`, `{profile}`.

**Why it breaks:** §4.2 freezes `driver.cmd: "./bin/loadgen --history {history_path} --seed {seed} --profile {profile}"`, and the design keeps it verbatim. It also lists `--clients N --ops N --keys N` as loadgen flags and says "Key space is derived from the profile name; smoke: 8, gate: 64, soak: 256". So the loadgen hardcodes a profile-name → (clients, ops, keys, mix) table, and the `profiles:` block in `prothesis.yaml` is decorative: you can edit `gate: { clients: 16, ops: 20000 }` to `{ clients: 1, ops: 1 }` and nothing changes, or edit the loadgen's constants and the config still reads 20000. That directly punches a hole in CRUCIBLE §E.2 ("narrowing `max_faults_per_world`, or shortening a profile budget are ALL lock changes") and §E.1: the lock manifest hashes `prothesis.yaml`'s profile budgets, but the value that actually governs the run lives in a Go constant the lock does not cover. An agent can weaken the gate by 10× by editing the driver, with a green lock.

**Fix:** Decide and specify the transport now. Simplest spec-compatible option: the driver supervisor exports the resolved profile as environment variables to the child (`PROTHESIS_CLIENTS`, `PROTHESIS_OPS`, `PROTHESIS_MIX_READ`, …) (no change to the frozen `cmd` template) and the loadgen *fails loudly* (exit non-zero) if they are absent rather than falling back to built-in defaults. Then extend the lock manifest to cover the driver binary's own SHA-256 alongside profile budgets. Record the env-var contract in DECISIONS.md; if you instead want to extend the `cmd` template, that is an OPEN_QUESTIONS.md entry since the template is normative.

### P5 [high] `KV_TAGS` (build arg) and `KV_VARIANT` (image tag) are independent, so `KV_TAGS=kvfixed docker compose build` produces the *patched* binary tagged `prothesis/kvfixture:buggy`.

**Why it breaks:**

```yaml
build: { args: { KV_TAGS: "${KV_TAGS:-}" } }
image: prothesis/kvfixture:${KV_VARIANT:-buggy}
```
Nothing couples them. Run `provebug --expect-clean` once with `KV_TAGS=kvfixed` and the local `prothesis/kvfixture:buggy` tag now points at the fixed image. Every subsequent `docker compose up` **without** `--build` silently runs the fixed fixture, and every Phase 2/3/4/5 run reports PASS while everything (compose, `thesis up`, the verdict) says "buggy". This is the worst possible failure mode for a tool whose entire value proposition is "we found the known bug": a false green that looks identical to a true green.
Separately, keeping `lease_fixed.go` in-tree behind a build tag is exactly the I6 / CRUCIBLE §E gaming vector: a Phase 6 agent facing a failing gate can flip a build arg instead of writing a fix. The design notes this in its own risk list and then ships it anyway.

**Fix:** Derive the tag from the arg in one place: `image: prothesis/kvfixture:${KV_TAGS:-buggy}` (so an empty `KV_TAGS` yields `:buggy` and `kvfixed` yields `:kvfixed`), or drop `KV_VARIANT` and require `--build` on every `up`. Additionally, have the kv binary report its build tag at `/status` (`"variant":"buggy"|"kvfixed"`) and have `thesis up` record the **resolved image digest** in the world file and verdict: the design's own risk list demands this and no part of the design implements it. Best of all: move the fix out of the tree. Ship only `lease.go`; keep the patched version as a `golden/lease_fixed.go.patch` that Phase 5's regress harness applies to a scratch copy, so the fixed binary is never buildable from the default source tree.

### P6 [medium] The design silently redefines the normative wildcard target `kv:*` and the quorum target `minority(kv)`.

**Why it breaks:** Spec §4.2 declares nodes as `- id: n1 / service: kv`, `- id: n2 / service: kv`, `- id: n3 / service: kv` and then targets them with `node: "kv:*"`; §4.3 defines `TARGET` as "wildcards (`kv:*`)" and "quorums (`minority(kv)`, `majority(kv)`)". Under that config, `kv` is the **service name** and `*` is the instance wildcard. The design renames the services to `kv-n1/kv-n2/kv-n3` and states: "`kv:*` and `minority(kv)` / `majority(kv)` resolve over nodes whose *service* matches the glob `kv*`"; i.e. the token before the colon is reinterpreted from an exact service name into a prefix glob. That is an alteration of frozen grammar semantics made in a parenthetical ("No new schema field; `mesh` is naturally excluded"), and it silently changes the meaning of the frozen constraint string `"never partition more than minority of kv"`.
The underlying conflict is real and worth surfacing: Docker Compose cannot have three services named `kv`, so the spec's own §4.2 sample is not expressible on the `compose` backend without `deploy.replicas`/scaling. Rule 4 says "If a requirement is unimplementable as written, stop and document the conflict in `OPEN_QUESTIONS.md`. Never silently relax a requirement." The design relaxes it silently.

**Fix:** Either (a) keep `service: kv` for all three nodes and use compose `scale`/`deploy.replicas`, so `kv:*` keeps its spec meaning; or (b) keep the `kv-n1..3` service names but do **not** touch the resolver; group by an explicit label. Whichever you pick, write an OPEN_QUESTIONS.md entry quoting §4.2's three-nodes-one-service block against Compose's unique-service-name rule, and a DECISIONS.md entry stating exactly how `kv:*` and `minority(kv)` resolve. Do not let the resolver's glob semantics be an emergent property of a service naming choice.

### P7 [medium] Phase 0's health-probe resolution is unspecified where it is actually hard: `{port}` is ambiguous and `docker compose port` returns an unusable address on Windows.

**Why it breaks:** This is the one place the design touches Phase 0 DoD (a) and it hand-waves: "poll the configured `harness.health[].probe` from the host, resolving `{host}`/`{port}` via `docker compose port`." Each kv container exposes **two** ports (8080 client, 9090 peer) and publishes one (`18081:8080`), so `{port}` has no defined referent: `docker compose port kv-n1` requires a container port argument the schema does not supply. And on Windows, `docker compose port kv-n1 8080` prints `0.0.0.0:18081`; substituting that into `http://{host}:{port}/healthz` yields `http://0.0.0.0:18081/healthz`, which Go's dialer will not reliably connect to on Windows. So the very first `thesis up` fails, in the first command of Phase 0, for reasons the design never mentions.

**Fix:** Pin the rule now and record it in DECISIONS.md: `{port}` = the host-side port of the node's *first* published port mapping (or add a `port:` field to `harness.health[]`; a schema addition, therefore an OPEN_QUESTIONS.md entry first). Normalize the `docker compose port` result: rewrite `0.0.0.0` and `::` and `[::]` to `127.0.0.1` before substituting. Add a `thesis up` integration test that asserts the resolved probe URL literally, so this cannot regress. Note that `harness.health[].node: "kv:*"` also depends on finding #6 being settled first.

### P8 [medium] The images and compose service definitions foreclose three of the fault families that the fixture's own `prothesis.yaml` puts in `allow:`.

**Why it breaks:** The fixture config allows `net.latency`, `net.loss`, `proc.kill`, `proc.pause`, `clock.skew`, `io.latency` and CRUCIBLE §A additionally requires `net.reorder`, `net.bandwidth`, `io.error`, `io.fill`, `mem.pressure`, `fd.exhaust` in Phase 2. Phase 2's DoD is "Every fault kind can be injected and cleanly withdrawn." But:
- The `kv` image is `alpine:3.20` + one static binary. No `iproute2`, no `iptables`, and no `cap_add: [NET_ADMIN]` on any service. So the §4.3-sanctioned `tc`/`netem`/`iptables`-in-namespace path is unavailable *by construction*, and the design's own escape hatch ("`tc`-based L3 injection inside containers remains available later if higher fidelity is ever needed") is false as written.
- `clock.skew(ms)` / `clock.jump(ms)` have **no mechanism at all**. There is no `libfaketime` in the image, and Linux time namespaces need `CAP_SYS_ADMIN` plus an `unshare --time` entrypoint: neither is present, and time namespaces do not shift `CLOCK_REALTIME` anyway. `clock.skew` is nevertheless in `allow:`.
- `io.latency(ms)` / `io.error(rate)` have no mechanism. The design asserts the WAL "gives `io.latency` / `io.error` faults something real to hit", but hitting requires a FUSE shim or `dm-delay` under the named volume; neither is designed.
Adding caps or packages later changes the image digest, which the design's own anti-gaming story wants recorded in the world file and verdict, so retrofitting is lock churn on top of rebuild churn.

**Fix:** Decide per family now and put it in `prothesis.yaml`/`DECISIONS.md`: add `iproute2` + `iptables` to the kv image and `cap_add: [NET_ADMIN]` to the kv services **in Phase 0** even though nothing uses them until Phase 2 (cheap, and keeps the L3 path open); move `clock.skew` from `allow:` to `deny:` for this fixture with an OPEN_QUESTIONS.md entry stating that spec §4.3's libfaketime/time-namespace mechanism is not implementable in the alpine/Docker-Desktop configuration; and either add a FUSE/`dm-delay` data path for `io.*` or deny those too. An `allow:` list containing kinds the fixture cannot support guarantees the Phase 2 DoD fails on the only fixture we have.

### P9 [medium] The `mesh` ambassador lives inside the *fixture's* compose file, which pushes Phase 2's `net.*` injector into depending on target-supplied infrastructure.

**Why it breaks:** CRUCIBLE §L is normative: PRO-THESIS "must work on **unmodified** systems today (rules out requiring instrumentation)", and "oracle and world formats must be portable across repos, not tied to one project's layout." The design makes `net.partition` on the fixture mean "`POST /rules/bulk` to a service the fixture ships, on a port the fixture chose, with a rule schema the fixture defines", and declares "A node **only ever dials mesh URLs** ... That is a fixture invariant." Phase 2's perturber then either hard-codes that private admin API (portable to exactly one repo) or grows a second, real implementation that has never been exercised: in which case the design's claim that "Phase 2 requires no topology re-architecture" is wrong, because the real path is the one that was never built.
The invariant is also unenforced: all three kv nodes sit on the shared `kvclient` network and bind the peer listener to `0.0.0.0:9090`, so `kv-n1` can reach `kv-n2:9090` directly. Any future direct dial (leader forwarding, a catch-up shortcut, a debug endpoint) silently defeats every partition, and every subsequent PASS is meaningless with no visible symptom.

**Fix:** Pick one architecture and state it in DECISIONS.md: (a) PRO-THESIS *injects* a generic per-edge ambassador into any compose topology it manages; in which case the mesh belongs in `internal/perturber/faults/`, not in `testdata/kvfixture/`; or (b) the mesh is a fixture-only convenience, and the real `net.*` dispatcher uses `docker exec` + `tc`/`iptables` inside the container netns (which requires finding #8's image changes) with the mesh kept only as a cross-check. Independently, enforce the mesh invariant mechanically: bind the peer listener to the container's `kvpeer` interface address only (not `0.0.0.0`), and add a `raft_test.go`/boot-time assertion that every entry in `KV_PEERS` resolves to the mesh service.

### P10 [medium] `t_ns` is captured inside the history writer's mutex rather than at the true invoke/response instant, and this is presented as a correctness feature.

**Why it breaks:** §4.4 quoted: "**Writer discipline:** one `bufio.Writer` behind one mutex, and **`t_ns` is taken inside the mutex immediately before the write**. The file is then monotonically nondecreasing in `t_ns`, so append order equals time order ... it removes a whole class of checker bugs."
A linearizability checker's entire input is the real-time interval [invoke, ok] of each operation; the only orderings it may rely on are non-overlapping intervals. Timestamping at flush time replaces those intervals with "when this goroutine won the mutex". At the `soak` profile (64 clients) contention is real, so an `ok` record for an op that truly returned at t=100 can be stamped 105 while another client's `invoke` that truly happened at t=101 got the lock at 102: the log now shows the two overlapping when in reality they did not. Widening overlap permits *more* linearizations, which **hides** real violations; narrowing on the other side can manufacture spurious ones. Either way the history is no longer a faithful record, and this is invisible: the file looks pristine and monotone. It undercuts I2 ("Every Failure is a Seed") and CRUCIBLE §M's soundness rule just as surely as a mis-classified timeout does: the design correctly identifies the `ok`/`fail`/`info` table as "the soundness lynchpin" and then compromises the other half of the same soundness argument.

**Fix:** Capture `t_ns` at the true event (immediately before writing the request in the client goroutine for `invoke`, immediately after reading the response for `ok`/`fail`/`info`) using a single monotonic base captured at process start. Then either (a) let records land out of order and sort by `t_ns` at parse time, or (b) buffer per-client and merge-sort on flush. If a monotone-append file is genuinely wanted, add a *separate* `seq` field for append order and leave `t_ns` truthful. Add a test asserting that recorded intervals are contained in the true intervals measured around the HTTP round trip.

### P11 [medium] The Raft sketch as written contains additional latent safety bugs beyond the injected one, which voids the premise that justified hand-rolling Raft.

**Why it breaks:** §1's decisive argument against `hashicorp/raft` is: "it is an opaque blob inside the one artifact whose entire purpose is to have **exactly one** known defect ... we cannot distinguish 'PRO-THESIS found our injected bug' from 'PRO-THESIS found a library bug'". The sketched `onAppendResponse` reintroduces exactly that ambiguity:
```go
func (r *Raft) onAppendResponse(peer string, resp appendResp) {
	if resp.Term > r.currentTerm { r.becomeFollower(resp.Term, ""); return }
	if !resp.Success { r.nextIndex[peer]--; return }
	r.lastAckTick[peer] = r.tick
	...
	r.maybeAdvanceCommit()
}
```
- No `if r.role != RoleLeader { return }` guard. A node that has stepped down still updates `matchIndex` and calls `maybeAdvanceCommit()`.
- No stale-response guard (`resp.Term < r.currentTerm` → drop). A response to an RPC sent in an older term is processed as current: a classic source of committed-index corruption.
- `r.nextIndex[peer]--` is unguarded and can go to 0 and underflow `uint64`, and it decrements on responses to superseded requests.
Under exactly the conditions the fixture is designed to create (multi-second freezes, blackholed RPCs with 250 ms timeouts, responses arriving many terms late through the mesh), these will fire. A resulting anomaly is indistinguishable from the lease bug in the verdict, and `provebug --expect-clean` on the `kvfixed` build can then fail for a reason nobody injected.

**Fix:** Add all three guards. Then make the "one defect" claim testable rather than asserted: `raft_test.go` should run a deterministic in-process cluster (no HTTP, no Docker) over randomized partition/freeze schedules, with the buggy `leaseHeld()` replaced by the correct one, and assert Raft's five Figure-2 safety properties (Election Safety, Leader Append-Only, Log Matching, Leader Completeness, State Machine Safety) over thousands of seeds. That test is what licenses the "exactly one defect" argument; without it the argument is a claim, and §1's own reasoning says a claim is not enough.

### P12 [medium] `golden/witness.json` is specified without the normative `schema` and `valid_phases` fields, and the history log's `value` field changes type for txn ops.

**Why it breaks:** Rule 2: "All schemas ... are **normative**. Do not invent, alter, or improvise field names or semantics."
- §4.5 output is `{"schema": "prothesis.oracle_output/v1", "oracle": ..., "class": ..., "valid_phases": ["ASSERT"], "status": ..., "witness": ..., "explanation": ...}`. §6 of the design specifies the golden file as `{"oracle":"linearizable.kv","class":"consistency","status":"violated","witness":{...},"explanation":"..."}` and calls it "a `prothesis.oracle_output/v1`-shaped blob". It is missing `schema` and `valid_phases`. Because this file is explicitly "the golden file" that Phase 3's oracle is written and unit-tested against, the omission propagates into the real oracle's output.
- §4.4 shows `value` as a scalar (`"value":7`). §4.4 of the design emits `"f":"txn", "value":[["r","k/3",null],["w","k/7",30000123]]` and drops `key`. Reusing a normative field with a different type is an alteration of its semantics, however pragmatic. It is defensible (Elle's rw-register convention) but it is not free.

**Fix:** Add `"schema": "prothesis.oracle_output/v1"` and `"valid_phases": ["ASSERT"]` to `golden/witness.json`, and validate all three golden files against `pkg/schema` types in a fixture test (this also forces `pkg/schema` to exist early, which serves Phase 0). For the txn encoding, write an OPEN_QUESTIONS.md entry quoting §4.4's scalar `value` and stating the chosen txn representation, rather than treating "keeping `value` as the normative field name" as sufficient fidelity: the name is preserved but the type is not.

### P13 [medium] Gating Phase 0 on `provebug` exiting 0 front-loads the entire fixture (Raft + mesh + loadgen + steady + provebug) before any `thesis` binary exists.

**Why it breaks:** §7 of the design: "Only after `provebug` exits 0 does Phase 0 of `thesis` begin." But Phase 0 DoD (a) ("`thesis up && thesis down` boots and tears down the KV fixture cleanly") needs only three kv containers with a working `/healthz` and a compose file. It does not need the mesh (nothing calls its admin API until Phase 2, as the design itself notes), the loadgen (Phase 1), `steady` (Phase 1, SEED), or `provebug` (which proves a Phase 2/3 property). Meanwhile Core Rule 5 is "**Always Ship a Compiling Binary**: Every phase must produce a fully functioning `thesis` binary." Sequencing days of Raft and race-reproduction work ahead of the first `thesis` command means the longest, riskiest stretch of the project has no shippable binary and no external checkpoint, and `provebug` is the single most likely thing to stall, because making a timing anomaly deterministic is the hardest part of the fixture.
Phase 0 DoD (b) (byte-identical `.thesis` round-trip) is also entirely untouched by this design; it needs `pkg/schema` + `internal/recorder`, which have no dependency on the fixture at all.

**Fix:** Split the prerequisite: build kv node + Dockerfile + compose + `/healthz` + `/status` first (that is what `thesis up`/`down` needs), then do Phase 0 of `thesis` end to end, then return for mesh/loadgen/steady/provebug before Phase 1's driver work. Keep §7's build order for the fixture internally, but do not make `provebug` a gate on Phase 0. Explicitly note that DoD (b) is orthogonal and can be satisfied before the fixture boots at all.

### P14 [low] `connection_count` will be near-constant on this host, weakening the Phase 4 state-abstraction tuple it is chosen to feed.

**Why it breaks:** §4.2 specifies `http.Transport` with `MaxConnsPerHost = clients` and "keep-alives on", with the loadgen on the Windows host reaching containers through Docker Desktop's port proxy. Keep-alived connections are established early and held, so each node's `ConnState`-derived count saturates near its share of `clients` and stops moving. Spec §6 Phase 4 lists the tuple as `(role, term, bucketed_queue_depth, connection_count)` and CRUCIBLE §F adds bucketed lag; a dimension that takes one value contributes nothing to "count distinct GLOBAL tuples", so the coverage signal driving I4's search is quietly one dimension poorer than the design claims. There is also an unresolved ambiguity: the node runs two HTTP servers (8080 client, 9090 peer) and the design does not say which one `connection_count` counts; the peer-plane count is the one that actually varies under partition.

**Fix:** Report both counts separately in `/status` (`client_connections`, `peer_connections`) and use the **peer** count in the coverage tuple, where partitions and freezes actually move it. Bucket it (`0, 1, 2, 3+` on n=3) rather than using the raw integer, matching the treatment of `queue_depth`.

### P15 [low] Several load-bearing claims about Docker behaviour and the Raft loop are stated as verified when they are not.

**Why it breaks:** - "**`docker compose down` HANGS on a paused container.**" This was true under cgroup v1, where SIGKILL cannot be delivered to a FROZEN task. Docker Desktop's Linux VM runs cgroup v2, where SIGKILL *does* reap frozen tasks, and moby's `daemon/stop.go` special-cases paused containers. So the claim is probably false on Docker 29.1.3 here. It is used to justify a Phase 0 requirement.
- "A **no-op entry appended on election** ... Commits in ~1 RTT (≈5 ms), so a new leader is write-serving ~10 ms after winning." `applyCommitted()` is called only from `onTick()`, so apply granularity is `TickInterval` = 25 ms, not 10 ms. The §2.2 derived figure "time from fault to a committed new-term write ≈ ≤950 ms" inherits the error.
- `r.peerIDs()` is used throughout `leaseHeld`, `maybeAdvanceCommit`, and `broadcastAppendEntries`. If it ranges a Go map, iteration order is randomized per process, injecting gratuitous nondeterminism into broadcast order: against the design's own §1.3 boast about scoring well on `thesis doctor`'s determinism readiness (CRUCIBLE §C).
- The `Raft` struct declares `bootMono time.Time` and no `clock` field, yet `onAppendResponse` and `lease_fixed.go` both call `r.clock.Monotonic()`. `/status` returns `role_hint` described as a "Static label from `prothesis.yaml`", but nothing passes it into the container.

**Fix:** Keep the unpause-before-down ordering (it is correct hygiene regardless) but restate the justification as "defensive, unverified on cgroup v2" rather than asserting a hang, and verify it once the daemon is up, since a false premise here will be copied into `internal/harness`. Call `applyCommitted()` from `step()` as well as `onTick()`, or drop the 10 ms figure. Make `peerIDs()` return a sorted slice computed once at construction. Add the `clock Clock` field to the struct and plumb `KV_ROLE_HINT` (or drop `role_hint` from `/status`, since PRO-THESIS already knows it from the config).

## Missing

- Phase 0 DoD (b) ("A world configuration round-trips through `.thesis` serialization byte-identically") is not addressed anywhere. The fixture design touches only DoD (a). Fair as scoping, but nothing in this design pins the serialization decisions that byte-identity depends on (map key ordering, float formatting, integer vs string durations, LF-only line endings, trailing newline, whether the round-trip is bytes→struct→bytes or struct→bytes→struct→bytes). The `.gitattributes` note marking `*.thesis` as `-text` is the only relevant sentence in the document, and on a Windows host without a git repo yet, that is the single highest-risk item for DoD (b).
- Log output format and volume from the kv node. CRUCIBLE §F ranks log-template coverage as signal #2 and says "**implement this FIRST** ... Highest signal-to-integration-cost ratio in the whole system", and spec §6 Phase 1 requires `no_panic_log` ("Log regex scan for panics, OOMs, and fatal crashes") and Phase 4 requires log-template normalization. The fixture is the only system those will ever be tested against, yet nothing in this design specifies what the kv node logs, at what level, in what format, or how many distinct templates it emits. A fixture that logs ten lines total makes log-template coverage untestable and Phase 4's benchmark meaningless.
- Where container logs go, and how the harness collects them. §4.1 `TEARDOWN` requires "Collect logs/artifacts"; `no_panic_log` needs a log stream; the causal timeline in §4.6 contains `{"event": "log", "node": "n1", "detail": "elected leader term 5"}`, so log lines must be timestamped and attributable per node and correlatable with the host virtual clock. The design captures a single host↔VM clock offset at BOOT from one `/status` reading and stops there: no `docker compose logs` strategy, no per-line timestamping decision, no drift handling over an 8 h soak.
- `telemetry.json` for real runs. §4.5's oracle input requires `telemetry_path`. `provebug` emits a one-off `golden/telemetry.json`, but nothing defines the sampling loop that produces it during a real world: sample interval, which `/status` fields, how the frozen-node `role:"unreachable"` tuple is encoded on disk, or the file's schema. Phase 1's `no_unbounded_queue` and `resource_return_to_baseline` both read it.
- `steady_state` semantics. §4.1 `SEED` is "Load initial state; wait for `steady_state` probe to succeed" and the fixture config points at `./bin/steady --timeout 60s`, but what `steady` actually checks (leader elected? all three `last_applied` equal? N seeded keys present?) and what initial state gets loaded are never specified. `cmd/steady` appears in the tree with a one-line comment.
- How `./bin/loadgen(.exe)` and `./bin/steady(.exe)` get built. `driver.cmd` is a relative path into `testdata/kvfixture/bin/`, and §9 mentions a `.exe` fallback, but no build step, Makefile target, or PowerShell script produces those binaries, and §7's fixture build order does not include the build. On a host where Git Bash is broken, this needs to be a `.ps1` or a Go `//go:generate`, decided now.
- The `thesis init` scaffolded template. Phase 0's deliverables list `cmd/thesis` with `init`, and the design mentions in one clause that "`thesis init`'s *template* still mirrors §4.2", including the `pg`/postgres node and the `"pg must be reachable during SEED"` constraint that the fixture drops. Nothing else about `init` is designed, though it is one of only three Phase 0 CLI commands.
- `.prothesis/` directory layout beyond `runs/`. The design introduces `.prothesis/state/up.json` in passing. The spec references `.prothesis/oracles`, `.prothesis/runs`, `.prothesis/lock`, and `.prothesis/regressions/`. Phase 0 creates the state dir, so the layout should be fixed now, particularly whether `.prothesis/state/` is gitignored while `.prothesis/regressions/` is append-only and committed (CRUCIBLE §E.4).
- A second, harder fixture defect. The design's own risk list identifies this correctly: the lease bug is findable with a single fault, so Phase 4's DoD ("Statistically outperforms uniform random fault injection across 10 benchmark trials") has no bug that genuinely requires the overlap that CRUCIBLE §G's mutation bias exists to produce. No candidate defect is proposed, and the choice constrains fixture architecture (it should be designed alongside the lease bug, not bolted on in Phase 4).
- Image digest recording and lock coverage of harness build args. The design's own risk list demands that "the lock manifest must cover harness build args and record resolved image digests in the world file and verdict, or the whole fail-closed story has a hole in it", and then no section implements it. Given finding #5 (`KV_TAGS`/`KV_VARIANT` decoupling), this is the mechanism that would have caught a silently-fixed image, and it is absent.
