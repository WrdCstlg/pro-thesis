# 08-saboteur.phase0-reachback.verify

## Verdict

**NEEDS-REVISION**

## Overreach check

Yes, in two places, and both are dressed as forward compatibility.

(1) THE ENTIRE TELEMETRY SECTION. Phase 0's pkg/schema deliverable is explicitly scoped: "Define Go types for `prothesis.yaml`, `.thesis` world files, history logs, and verdicts." Telemetry is not in that list, and internal/recorder's Phase 0 scope is "virtual clock, deterministic PRNG seed streams, and `.thesis` world serialization/deserialization." The analysis nonetheless specifies six new schema types plus `internal/recorder/telemetry.go`: "Implement TelemetryWriter appending records to telemetry.jsonl". The repo's own D-006 already fixed the permitted Phase 0 reach at exactly two items ("the `search:` configuration block (A.10) belongs in `pkg/schema` now" and "A.8's determinism requirement constrains the `internal/recorder` PRNG stream derivation now") and telemetry is neither. Compounding it, the analysis invents the schema identifier `prothesis.telemetry/v1` silently while, in the very next breath, flagging `prothesis.world/v1` as "an invented schema name in a document that forbids inventing field names" requiring both a DECISIONS and an OPEN_QUESTIONS entry. Rule 2 is applied to one invention and not the other. And as the first confirmed finding shows, the invented schema is wrong.

(2) MCTS PROVENANCE IN THE FROZEN WORLD FORMAT. `Meta.TreeID` and `Meta.TreePath []int` encode a specific MCTS implementation (ordered children with stable integer indices) before Phase 4 exists to say whether those indices are stable under A.7's ladder prior and progressive widening. The justification given is: "adding an enum *value* later is additive and cheap; adding the *field* later is a format break that invalidates every committed regression world." That justification is false under the analysis's own design. It states "`WorldMeta` is provenance. It is EXCLUDED from WorldHash", and every Meta field except Origin is `omitempty`. A hash-excluded, omitempty provenance field can be added in Phase 4 without changing any world's hash and without invalidating any committed world a newer binary reads. The stated reason to commit now does not hold, which leaves the commitment as Phase 4 design smuggled into a frozen Phase 0 format behind a false forward-compatibility argument.

What is NOT overreach and should be defended against a reviewer who over-corrects: the named-exported-verdict-types delta, domain-keyed PRNG derivation with the golden vector test, canonical JSON with no maps and no bare floats, and the strict-decoder round-trip DoD. Those are genuinely Phase 0 format work that Phase 0 freezes anyway.

## Confirmed problems (12)

### P1 [high] The proposed prothesis.telemetry/v1 schema omits every signal OBSERVE is normatively required to read. A.3 says the telemetry trajectory captures `(queue_depth, retry_count, active_connections, error_rate, role)` per node; A.2's OBSERVE box lists "queue depth / retry count / conn pool / error rate / role changes"; three of A.3's four REINFORCE criteria are stated in terms of queue depth, retry count, and role change. The analysis's TelemetrySample carries only rss_bytes/cpu_pct/fd_count/task_count/goroutines. queue_depth, retry_count, active_connections and role have NO field anywhere in the format. error_rate exists only on TelemetryDriver, which the analysis explicitly annotates "Run-scoped, not per-node" - directly contradicting A.3's "per node".

**Why it breaks:** The analysis freezes this as a Phase 0 cross-repo format and asserts "Phase 4 can then adopt 200ms, 500ms, or a probe-mode override without any format change." But the format cannot express the classification A.9's DoD #1 requires (classify proc.pause on the leader as REINFORCE_ACCELERATING). Worse, it breaks in Phase 1, not Phase 4: base spec Phase 1 built-in oracle 3 is `no_unbounded_queue` - "Monotonically increasing queue depth across QUIESCE" - and there is nowhere to record queue depth.

**Fix:** Either (a) drop the telemetry schema from Phase 0 entirely, or (b) if kept, add a per-node application-signal record carrying queue_depth, retry_count, active_connections, error_rate and role, and move error_rate to per-node granularity as A.3 requires. Option (a) is preferable - see the overreach finding.

### P2 [high] DefaultConfig() + decode-in-place is unsafe for the frozen config schema's map-valued sections, and the analysis's probe never tested them. It generalises from nested structs (search.utility, search.observe) to a schema whose lock-covered parts - `profiles`, `driver.profiles`, `driver.profiles.*.mix` - are Go maps. I ran this against yaml.v3 v3.0.1: (1) map ENTRIES do not merge - seeding defaults then decoding `profiles: {soak: {worlds: 5}}` yields soak with budget="" and driver_profile="", so the defaults inside the entry are silently destroyed; (2) map KEYS do merge, so a user who DELETES `soak` from prothesis.yaml still gets a fully-populated `soak` back from the compiled-in defaults (verified: "soak SURVIVED deletion by the user: true"); (3) KnownFields(true) does not protect map keys - a typo'd profile name `gaet:` decoded with err=nil and silently created a phantom profile.

**Why it breaks:** The mechanism's stated property - "yaml.v3 sets only the fields physically present in the document and does not zero the struct first - including recursively into nested structs" - is false for structs inside maps, which is exactly where the frozen schema puts profiles. A partial profile entry produces a zero Duration budget with no error, and Validate() as written checks nothing about profiles. It also holes the anti-gaming claim: under `config_digest = sha256(json.Marshal(resolvedConfig))`, deleting a lock-covered profile produces NO digest change because the default was resurrected. CRUCIBLE E2 makes profile budgets lock changes; this makes profile deletion invisible to the lock.

**Fix:** Do not pre-seed map-valued config sections in DefaultConfig(). Decode maps from the document only, then apply per-entry defaults explicitly after decode. Add profile validation to Config.Validate(): non-zero budget, non-empty driver_profile, worlds != 0. Record in DECISIONS.md that KnownFields protects struct fields only, and add an explicit allowed-key check wherever a map's key vocabulary is closed.

### P3 [high] `config_digest = sha256(json.Marshal(resolvedConfig))` over the RESOLVED, defaulted config turns every `thesis` binary upgrade into an exit-4 ORACLE_DRIFT incident. The analysis presents catching "a change in a compiled-in default" as the feature that makes resolved-config digesting superior to raw bytes. I verified the consequence: changing one compiled-in default with zero user config change moves the digest (33daeba01b30849d -> ff89213ea02a21d8).

**Why it breaks:** I6 and CRUCIBLE E1 specify that a lock mismatch "returns exit 4 and REFUSES TO RUN", and CRUCIBLE I tells the agent loop to "stop, escalate to human, NEVER auto-resolve" on code 4. So shipping a release that adjusts any default - or a Go version that changes float shortest-representation, since the config contains floats (exploration_constant, duration_penalty, driver mix ratios) - halts every downstream project pending a human `thesis oracles lock --reason`. Second bite: ConfigDigest is a hashed field of World and the analysis puts it inside WorldHash, so the same upgrade rewrites the hash of every world in the committed append-only regression corpus, breaking Meta.Parent chains and corpus dedup. Third: the analysis bans bare floats from the world file because "shortest-repr changes across Go versions" kill byte-identical round-trip, then feeds floats into the digest it embeds in that same world file.

**Fix:** Digest the user-supplied config normalised (parsed and re-serialised canonically, defaults NOT filled in) rather than the resolved config, so compiled-in defaults are out of scope; or split into a `config_digest` over user-authored settings for the lock plus a separate `tool_version` field for provenance. Exclude ConfigDigest from WorldHash either way. Ban floats from the digest input the same way they are banned from the world file.

### P4 [high] The analysis has zero findings on I5, one of the two constraints the task named as load-bearing. It never engages with the collision between A.5's "Early termination: If an oracle violation is detected during `DRIVE` or `PERTURB`, terminate the rollout immediately and backpropagate the full violation reward" and I5 / section 4.1, which place oracle evaluation in ASSERT after HEAL and QUIESCE and make consistency oracles ASSERT-only. The repo's own OPEN_QUESTIONS.md already carries this as OQ-004, with the sharpest form of the argument the analysis missed: consistency is the highest-reward class in A.6 (100 x 1.5) and the class the fixture bug belongs to, and it is precisely the class that cannot be soundly evaluated during DRIVE/PERTURB - so as written, early termination fires only on the low-value classes and biases the Saboteur away from the bug it exists to find.

**Why it breaks:** This is a Phase 0 format question, not only a Phase 4 one. If rollouts can terminate before ASSERT then A.6's `result.DurationSeconds` is not "wall duration, BOOT..TEARDOWN" as the analysis defines WorldResult; the world's `PhasePlan []PhaseTiming` must be able to express a truncated run; and the verdict's `violations[].phase` plus the oracle contract's `valid_phases` are what make a mid-DRIVE detection admissible. None of that is addressed - the WorldResult and Verdict types are built on the unexamined assumption that every world runs to TEARDOWN.

**Fix:** Adopt OQ-004's direction as a Phase 0 format constraint: early termination is admissible only for oracles whose valid_phases include the observing phase. Make PhaseTiming able to represent a truncated plan, define WorldResult.DurationSeconds as the executed duration rather than a full-lifecycle duration, and state the valid_phases/violations[].phase relationship in DECISIONS.md before the verdict types are frozen.

### P5 [medium] The stated repo state is wrong, and the consequences are substantive. The analysis opens with "The tree currently contains only `go.mod`" and "every delta below is a greenfield commitment." In fact DECISIONS.md (7883 bytes, D-001 through D-006) and OPEN_QUESTIONS.md (12883 bytes, OQ-001 through OQ-007) already exist and are substantial, and the repo layout directories are already scaffolded.

**Why it breaks:** Three concrete collisions. (1) Three of the five "ready-to-paste" OPEN_QUESTIONS entries duplicate live ones: the 200ms/500ms conflict is OQ-006.2 - which has already TAKEN a reading ("500 ms is the configurable default for general telemetry; 200 ms is the probe-specific trajectory rate"), so the analysis is less decisive than the repo already is - the two-level `search` key is OQ-005, and the A.6 class-coverage gap sits beside OQ-006.1. (2) The `D-00x` / `Q-00x` placeholder numbering collides with the live `D-00N` / `OQ-00N` scheme. (3) D-006 already fixes the permitted Phase 0 reach at exactly two items, and the analysis proposes far more without reconciling with it.

**Fix:** Re-derive the deltas against the actual DECISIONS.md and OPEN_QUESTIONS.md. Amend OQ-005 and OQ-006.2 rather than filing duplicates, number new entries from D-007 and OQ-008, and either justify each excursion beyond D-006's two-item scope or supersede D-006 explicitly.

### P6 [medium] The yaml.v3 dependency is assumed throughout without addressing the project's standing dependency policy. Every load-bearing config claim - `Decoder.KnownFields(true)`, decode-in-place, the KnownFields non-propagation trap - is a gopkg.in/yaml.v3-specific API. D-002 states: "The dependency posture follows from the directive's 'single, self-contained static binary' requirement... Standard library by default. Each dependency added must be justified in this file." go.mod currently has no require block at all.

**Why it breaks:** The recommended config mechanism is unimplementable in the standard library, so adopting it is a dependency decision D-002 requires be justified in DECISIONS.md. The analysis produces eleven DECISIONS entries and none of them is that one. If the dependency were rejected, the entire section 1 mechanism - the most detailed part of the analysis - would have to be rebuilt.

**Fix:** Add an explicit D-entry adopting gopkg.in/yaml.v3 under D-002's justification requirement, citing the KnownFields strictness that the anti-gaming argument depends on, and pin the version.

### P7 [medium] `rss_bytes` is mapped to cgroup v2 `memory.current`, which is not RSS. `memory.current` is the cgroup's total charged memory including page cache; anonymous RSS is `anon` in `memory.stat` (or `memory_stats.stats.anon` on the Docker stats API).

**Why it breaks:** This is the exact conflation error the analysis correctly condemns two paragraphs earlier for task_count vs goroutines - "reporting it as one would make `resource_return_to_baseline` assert something it is not measuring" - committed against its own Tier 0 list. Base spec Phase 1 oracle 4 compares RSS to a baseline within +/-N%. Page cache grows under a write workload and is reclaimed lazily, so `memory.current` will routinely fail to return to baseline after QUIESCE on a correct system, producing systematic false-positive resource violations in Phase 1.

**Fix:** Map rss_bytes to `memory.stat` `anon` (cgroup v2) or Docker stats `memory_stats.stats.anon`. If total charged memory is also wanted, add it as a distinct named metric, never as rss_bytes.

### P8 [medium] Making Seed a 16-lowercase-hex string leaves `{seed}` in `driver.cmd` undefined, and the analysis never chooses. Base spec section 4.2 fixes the driver command template as `"./bin/loadgen --history {history_path} --seed {seed} --profile {profile}"`, and CRUCIBLE H fixes the CLI as `thesis run [--seed N]`. The analysis decides the CLI "still accepts decimal... and canonicalises on write" but says nothing about what the harness substitutes for `{seed}` when it launches the driver.

**Why it breaks:** The driver is third-party and unmodified (CRUCIBLE L). A loadgen parsing `--seed` as a decimal integer receives `0000000000003039` and either errors out or, worse, parses it as decimal 3039 - silently a different workload from the one the world claims to encode, defeating I2 replay. This is a Phase 0 decision because the substitution lives in the harness/driver template Phase 0 scaffolds, and because the world file's seed spelling is frozen on first write.

**Fix:** Decide explicitly and record it: keep canonical hex in the world file, and define `{seed}` to substitute the unsigned decimal form (matching `--seed N`), adding a distinct `{seed_hex}` placeholder only if a use case appears. State it in DECISIONS.md alongside the hex-seed entry.

### P9 [medium] The `t_ns` epoch is invented and asserted as fact for a frozen schema. The analysis states "`t_ns` is the recorder's run clock in nanoseconds since run start - the same base as the history log." Section 4.4 specifies no origin. Its own example values are `1725300000000000`, about 1.7e15 - that is 19.97 days if read as nanoseconds since run start (implausible) and Sept 2024 if read as Unix epoch MICROseconds. Epoch nanoseconds for that date would be ~1.7e18, three orders of magnitude larger. Section 4.4's field name and its example values disagree, and the analysis silently picks a third reading.

**Why it breaks:** Directive rule 2 forbids improvising the semantics of a normative schema, and the analysis applies that rule scrupulously to `prothesis.world/v1` while breaking it here. External oracles are a portable cross-repo contract (CRUCIBLE L) and must correlate history `t_ns` against `oracle_input.phases` start_ms/end_ms; without a stated shared origin they cannot. The history log is an explicit Phase 0 pkg/schema deliverable, so this is frozen now.

**Fix:** File an OPEN_QUESTIONS entry that section 4.4's example values are inconsistent with the `t_ns` field name. Take a reading - run-relative nanoseconds is defensible and correlates cleanly with ms phase offsets sharing the same origin - and record it in DECISIONS.md as a chosen reading rather than a fact, stating the phases' origin normatively in the same entry.

### P10 [low] The stated rationale for the `exploration_constant: 1.41` decision is wrong. The analysis claims substituting math.Sqrt2 "would make any replay diverge from a world recorded under the literal - a subtle, hard-to-diagnose reproducibility failure that would surface only in Phase 4 as flaky MCTS replays."

**Why it breaks:** Under the analysis's own world-file design, `Faults.Realized` is authoritative and `thesis replay` executes the fixed realized schedule - the UCT exploration constant is never consulted during replay. The constant affects search, not replay, so it cannot make a replay diverge. Separately, A.10's own comment reads `exploration_constant: 1.41   # UCT exploration parameter (default: sqrt2)`, which literally states the default IS sqrt2; the analysis presents "the literal is normative" as settled when the addendum is genuinely ambiguous. The decision (use 1.41) is right; the argument a future contributor will read is false, which is exactly the failure mode a DECISIONS entry exists to prevent.

**Fix:** Rewrite the entry: 1.41 is what a user's prothesis.yaml literally contains, so the compiled-in default must match it byte-for-byte or `thesis` silently disagrees with its own scaffolded config and with config_digest. Note the A.10 comment ambiguity in OPEN_QUESTIONS rather than asserting it away.

### P11 [low] A quote-fidelity failure inherited from CRUCIBLE and never checked against the base spec. The Phase 0 delta for `cmd/thesis/init.go` says: "List all six built-in oracles including no_stuck_op (CRUCIBLE B)... where the base spec's sample YAML omits no_stuck_op that Phase 1 requires." Base spec section 4.2 `oracles.builtin` lists no_crash, no_panic_log, no_unbounded_queue, resource_return_to_baseline, availability_after_heal AND no_stuck_op - all six. CRUCIBLE B's claim about the on-disk file is false, and its heading ("requires SEVEN") contradicts the six names it then lists.

**Why it breaks:** The output is harmless (the same six oracles), but the analysis was asked to verify the spec itself and instead took a second-hand characterisation of it on trust - the same class of error that would have produced a fabricated conflict had the delta been non-trivial. It also means an internal inconsistency in CRUCIBLE B (seven vs six) went unlogged.

**Fix:** Drop the "correction" framing - section 4.2 already lists all six. File CRUCIBLE B's seven-vs-six discrepancy and its false claim about the on-disk section 4.2 as an OPEN_QUESTIONS note, since CRUCIBLE is being treated as normative content.

### P12 [low] The PRNG design contradicts itself between Derive() and the name registry. Section 4c defines `Derive(name, sub) => s.Get(name + "/" + sub)` for "per-world, per-node, per-tree-node" sub-streams, while test 4 in section 4d requires that names come "from one central `streams.go` const block" and that "`Get` on an unregistered name panics in tests." Derived names are by construction not in a const block. Separately, joining with "/" while the name regex permits "/" inside the sub segment makes derivation non-injective: Derive("a","b/c") and Derive("a/b","c") produce the same key.

**Why it breaks:** Both are Phase 0 deliverables the analysis wants shipped together, so the registry test and Derive cannot both be implemented as specified. The collision is a hole in a property the analysis elevates to normative ("depends only on (root, name)"), and two streams silently sharing a key is the precise failure the domain-keying exists to prevent.

**Fix:** Register PREFIXES rather than full names and have Get validate that a name's first segment is registered, or exempt Derive from the registry check explicitly. Use a separator the name grammar forbids, or length-prefix each segment inside deriveKey rather than concatenating.

## Missed by the analysis

- The telemetry format cannot carry queue_depth, retry_count, active_connections or role, which A.3 requires "per node" and which three of its four REINFORCE criteria are defined in terms of, and which Phase 1's `no_unbounded_queue` oracle also needs. This is the single largest miss and it forces a format change in Phase 1, not Phase 4.
- I5 gets no treatment at all. A.5's "terminate the rollout immediately" on a violation detected during DRIVE/PERTURB collides with section 4.1 and I5 (consistency oracles are ASSERT-only), and it is the highest-value oracle class that is excluded, so early termination structurally biases the Saboteur away from the fixture's stale-read bug. The repo already carries this as OQ-004; the analysis neither found it nor built its WorldResult/PhasePlan/Verdict types to accommodate a truncated run.
- No budget arithmetic was done, despite freezing `probe_budget_pct: 20` and `max_mcts_depth: 4` as validated Phase 0 defaults. At the gate profile's 600s budget those defaults give 120s of probing and 480s of escalation; at A.5's own "25-60 seconds each" that is 8-19 rollouts total. A depth-4 tree over the sample config's action space (7 allowed kinds x ~9 resolvable targets is already ~63 root actions) cannot be searched by 8-19 rollouts: no node reaches even 2 visits, so UCT's exploration term never differentiates and A.5's pruning rule ("visited >=3 times") is unreachable. The ladder prior does all the work and UCT is decorative. Related and also missed: A.3's "Cost: ~5-15s per probe" is inconsistent with A.5's 25-60s per real world execution, since a probe world is a real world; and A.3's per-kind-per-node sweep over the sample config is ~21 probe worlds, which does not fit in 120s at either cost estimate.
- The A.2 vs A.6 utility disagreement. The analysis reports that A.6 covers only 6 of CRUCIBLE's 8 classes but never notices that A.2's box (also labelled "Utility Function (normative)") lists only four (consistency 100, crash 80, resource 40, liveness 20), omitting safety (60) and convergence entirely. Two normative statements of the same function disagree. The repo already logs this as OQ-006.1.
- The closed `Class` vocabulary interacts badly with external oracles. `prothesis.oracle_output/v1` carries a free-text `class` field emitted by third-party executables, and CRUCIBLE L makes the accumulating oracle library the defensible asset. Typing Violation.Class as a closed 8-value enum and decoding strictly means a legitimate third-party oracle emitting a class outside the set is rejected rather than scored, while A.6 already scores two members of the closed set at zero. The analysis's rationale ("prevents typo'd class strings from silently scoring zero") is inverted: A.6 silently scores unknown classes zero by design.
- The claim that emitting telemetry.jsonl is "fully compliant" because "`telemetry_path` is the frozen FIELD NAME; the path VALUE is not frozen" skips the actual cost: changing the file's CONTENT format from a JSON document to JSONL changes what every external oracle in a portable cross-repo library must parse. Also unexamined: nothing prevents the recorder from writing JSONL internally for the Saboteur to tail while materialising a complete JSON document at ASSERT for oracles, which satisfies both readings, so the framing of the two as incompatible is not established.
