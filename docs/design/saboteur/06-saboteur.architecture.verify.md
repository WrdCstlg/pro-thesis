# 06-saboteur.architecture.verify

## Verdict

**NEEDS-REVISION**

## Overreach check

## Confirmed problems (14)

### P1 [high] The flagship parallelism enabler: 'Publish NO host ports; the harness reaches nodes by container IP'; is impossible on the verified environment. I tested it: `docker run -d nginx:alpine`, IP 172.17.0.2, `Invoke-WebRequest http://172.17.0.2/` from PowerShell times out. Container IPs are not routable from the Windows host under Docker Desktop's Linux engine.

**Why it breaks:** This is a Phase 0 delta against `testdata/kvfixture/docker-compose.yaml` and it collides with two frozen contracts. Base spec 4.2 defines health probes as `probe: "http://{host}:{port}/healthz"` executed by the harness, and `driver.cmd: "./bin/loadgen --history {history_path} ..."` runs as a host process writing to a host path. With zero published ports, neither can reach the kv nodes. The analysis's cited empirical proof ('My W=8 benchmark used per-project bridge networks and zero published ports and worked cleanly') proves only that compose up/down succeeds: it never issued an HTTP request from the host, which is the operation that actually fails. The PortLeaser is demoted to 'where host ports are unavoidable'; they are unavoidable here, so the fallback is the primary design and the whole W=4 plan rests on the one path that does not work.

**Fix:** Invert it. Phase 0 fixture publishes ephemeral host ports (`- "0:8080"`, i.e. dynamic host port), harness resolves the assigned port via `docker compose port <svc> 8080` after `up`, and `{host}`/`{port}` in the health probe template bind to `127.0.0.1:<assigned>`. The PortLeaser/flock is then unnecessary: the daemon allocates. The alternative (run loadgen and health probes as a sidecar container joined to the world network, reached via `docker exec`) is also viable but changes `driver.cmd` semantics and the `{history_path}` mount contract, so it is a bigger Phase 0 commitment; pick ephemeral published ports.

### P2 [high] A.5's probe budget is misquoted by omission, and the omitted half is the binding one. A.5 reads: 'Probe budget: First 20% of worlds (or first 20% of wall-clock budget, whichever is reached first).' The analysis quotes only the wall-clock clause ('A.5: probe budget = first 20% = 120 s') everywhere it appears.

**Why it breaks:** DoD #2's 10 minutes maps to `profiles.gate: { budget: 10m, worlds: 30 }`. 20% of 30 worlds = 6 worlds, and 'whichever is reached first' means the probe phase ends at min(6 worlds, 120 s). A 22-world sweep is 367% of the world cap. Parallelism does not help: running 22 worlds concurrently is still 22 worlds. So the headline mitigation ('Probe sweep 22 worlds / 4 x 21 s = 116 s, fits the 120 s budget') is invalid: it satisfies the clause it quoted and violates the clause it dropped. The same omission voids finding 2's mitigation: '480 s x 4 / 31 s = 62 rollouts' requires 62 worlds against `worlds: 30` (24 remaining after probes), so the ceil(2*sqrt(62)) = 16 root arms and '3.9 visits/arm' that justify 'the bandit starts to carry signal' cannot occur under the gate profile. Separately, even the arithmetic it did do is wrong: 22 worlds at W=4 is ceil(22/4) = 6 batches x 21 s = 126 s, not 116 s; it divided 22/4 = 5.5 and kept the fraction. 126 > 120 even on its own terms.

**Fix:** State the conflict as min(0.2*worlds, 0.2*wall) and resolve it explicitly: either (a) recommend the probe sweep be budgeted on wall-clock only and log the `worlds` clause as an OPEN_QUESTIONS.md conflict with A.5, or (b) accept the 6-world cap and make the ladder-ordered anytime sweep the whole answer (which the analysis already argues for, and which makes the W=4 parallelism argument unnecessary for probing). Also recheck the escalation plan against `worlds: 30`: under the gate profile the real rollout ceiling is ~24, not 62, and the 'UCT now carries signal' conclusion does not survive that.

### P3 [high] Finding 2's core claim: '(a) Every rollout hits an unvisited child, so backprop never influences a decision ... no node is ever visited twice ... UCT contributes exactly zero bits': is falsified by the analysis's own progressive-widening rule three sections later (section 3.3 step 8, C_pw = 2, alpha = 0.5).

**Why it breaks:** With PW the root's child count is capped at ceil(2*sqrt(n)), not the raw branching factor. At n = 16 rollouts the root has at most ceil(2*4) = 8 children, so children average 2 visits and UCT's exploitation term is a real 2-sample average that does influence selection. The 'b >= 16' premise holds only for an unwidened tree, which is not the tree being proposed. The word 'provably' is doing work the argument cannot support. The statistical-power argument (b) and the vacuous-regret argument (c) are both correct and survive on their own, but (a) is presented as the first and strongest of three independent reasons, and it is an artifact of comparing the raw action space against a design that never enumerates it.

**Fix:** Delete (a) or restate it correctly: under PW at 16 rollouts you get 8 arms at ~2 visits each, which is enough for backprop to fire but far below the n ~ 15/arm that (b) shows is needed. The honest claim is 'UCT is underpowered', not 'UCT is provably identical to first-play-urgency ordering'. The recommendation (invest in the prior, not tree depth) is unaffected; the justification must be.

### P4 [medium] The 249-action root cardinality: presented as computed and used as 'the quantitative proof that the ordering is the algorithm'; is inflated roughly 2x by including magnitudes that the analysis's own rung gate (section 3.3 step 3: 'Gated by rung: net.latency Low is Rung 0, net.latency High is Rung 1') excludes at seedRung = 2.

**Why it breaks:** A.7 names exactly these magnitudes at rungs <= 2: net.latency(50ms) and clock.skew(100ms) at Rung 0; net.latency(500ms), net.loss(5%), io.latency(200ms) at Rung 1; proc.pause at Rung 2. clock.skew(3000ms) is Rung 5 TEMPORAL, so clock.skew High must not appear at rmax = 2. io.latency High(800ms) and net.latency Med(200ms) have no rung at all in A.7; the invented 3-level table in section 3.2 assigns magnitudes A.7 never rungs. Recomputing under the analysis's own step-3 gate: proc.pause 5x1x3 = 15; net.latency 8x2x3 = 48; net.loss 8x1x3 = 24; clock.skew 5x1x3 = 15; io.latency 5x1x3 = 15. Total 117, not 249. The PW coverage figure is then 16/117 = 13.7%, not 6.4%.

**Fix:** Either recompute to 117 and restate the coverage figure, or explicitly declare the section 3.2 magnitude table a normative extension of A.7 that assigns rungs to the new levels (net.latency Med, io.latency High, net.loss Low/High, clock.skew Med) and record it in DECISIONS.md; at which point 249 becomes defensible. Right now the table and the enumeration rule disagree with each other.

### P5 [medium] The recommended fix for the novelty-dominance finding does not fix the counterexample it was written for. Finding: the 12-fault/120 s world with 5 novel templates scores 102 + 50 = 152 > 141. Recommendation: 'u += 10.0 * min(NewTemplates, noveltyCap) with noveltyCap default 5'.

**Why it breaks:** min(5, 5) = 5, so the capped world still scores 102 + 50 = 152 > 141. The cap is set exactly at the counterexample's value and changes nothing about it. To make parsimony bind against that specific case you need cap <= 3 (102 + 30 = 132 < 141), or the SearchUtility split, which the recommendation offers as an alternative ('and/or') rather than choosing. Since this finding is what threatens DoD #3 (<= 4 faults), a non-responsive fix here means DoD #3 stays exposed.

**Fix:** Choose the SearchUtility split as the primary remedy (it is the only one that also fixes the shallow-bias finding) and set novelty_cap by derivation, not by round number: the cap must satisfy 10*cap < 3*(faults_max - faults_min) for the fault range you want parsimony to dominate. For faults_max = 12, faults_min = 2 that is cap < 3. Default 3, not 5.

### P6 [medium] The PRNG stream table: the analysis's self-declared 'THE critical delta'; keys the `topology` and `driver` domains on **worldID**, but I2's world tuple is `(seed, topology_variant, driver_profile, fault_schedule, phase_timings)`. worldID is not in the tuple.

**Why it breaks:** Replaying a `.thesis` file necessarily assigns a new worldID (or an ID scoped to the new run), so `Derive("driver", worldID)` yields a different loadgen `{seed}` and `Derive("topology", worldID)` a different topology variant than the original execution. The world file would then not reproduce the world it describes: an I2 violation introduced by the very Phase 0 delta that claims to protect determinism. It also makes the Phase 0 DoD ('a world configuration round-trips through .thesis serialization byte-identically') vacuous, since round-tripping the file no longer round-trips the execution. Note the same table lists a `harness.ports` domain, which the port recommendation elsewhere makes dead.

**Fix:** Derive every world-scoped stream from the tuple, not from a run-scoped identifier: `NewStreams(world.Seed)` per world, and address topology/driver as `Derive("topology")` / `Derive("driver")` with no path. If a worldID is wanted for the search-scoped streams (`mcts.*`), define worldID := SHA-256 of the canonically-encoded tuple so it is a function of the tuple rather than of the run. Drop `harness.ports` once ports are daemon-assigned.

### P7 [medium] I5 is misapplied, and the analysis contradicts itself on it. Section 6.3 argues mid-world escalation 'would also violate I5 (assertions belong in ASSERT, after HEAL and QUIESCE)', but section 1.7 item 2 recommends 'Cancel the world's context the instant an oracle violation is observable during DRIVE/PERTURB' as 'required, not optional'.

**Why it breaks:** Both cannot be true. And the spec sides with section 1.7: I5 says 'Every oracle declares the specific lifecycle phases in which it is valid', Phase 3 deliverables say 'Invariant oracles evaluated throughout; convergence oracles evaluated strictly in ASSERT', and A.5 rollout policy #2 mandates exactly the early termination that section 6.3 calls an I5 violation. Only consistency/convergence oracles are ASSERT-only. Building the section 6.3 conflict on a misreading weakens a conclusion that is otherwise correct and important.

**Fix:** Drop the I5 clause from section 6.3. The argument stands on its own and is stronger without it: there is no fork primitive for a running 3-container compose topology, so a live-state root is unimplementable under I1, full stop. Keep the resolution (root = the probe prefix, every rollout re-executes from BOOT) and keep early termination: they are consistent with each other and with A.5 once I5 is removed from the picture.

### P8 [medium] The 200 ms vs 500 ms sampling conflict is half-manufactured. The analysis asserts 'A.3 says 200 ms; A.4 and A.10 observe.sample_interval_ms say 500 ms'. A.4's 500 ms is stated only for source #1, 'Container/process metrics: RSS, CPU%, FD count, thread/goroutine count'. A.3's 200 ms applies to a different tuple: `(queue_depth, retry_count, active_connections, error_rate, role)`. A.4 states no rate for its sources #2-#4.

**Why it breaks:** A.3 and A.4 are not in conflict as quoted; they rate different metric families, which is normal (resource metrics sample slower than driver metrics). The real and sufficient conflict is A.10's single `observe.sample_interval_ms: 500` knob, which cannot express two families at two rates, combined with `spiral_window: 5` giving a 2.5 s regression window against a 500-2000 ms probe fault window. Presenting this as an A.3/A.4 contradiction inflates a BLOCKING classification on a misquote, and it also misstates the fix: the problem is one knob for two families, not two documents disagreeing.

**Fix:** Restate as: A.10's single sample_interval_ms is underspecified for the two metric families A.4 enumerates. Split it into `observe.resource_sample_interval_ms: 500` (A.4 source 1) and `observe.driver_sample_interval_ms: 200` (A.3's tuple), and keep the derived constraint `spiral_window * driver_interval <= 0.5 * fault_window`. Drop the claim that A.4 contradicts A.3.

### P9 [medium] The lock-file urgency argument for landing the full `search:` block in Phase 0 misapplies CRUCIBLE section E. E.1 scopes the manifest to 'a hash manifest of every oracle definition, the allowed fault space, and profile budgets'; E.2 scopes lock changes to 'Removing a kind from allow, narrowing max_faults_per_world, or shortening a profile budget'. `search:` is none of those.

**Why it breaks:** Adding `search:` later is therefore not an ORACLE_DRIFT event, so 'a lock-bump ceremony later' is fabricated urgency. Worse, `.prothesis/lock` does not exist until Phase 3, so there is no Phase-0-specific deadline at all: Phases 1 and 2 are equally 'before the lock exists'. The argument is being used to license a Phase 0 schema commitment that the phase-order rule does not otherwise permit.

**Fix:** Drop the lock argument. If `search:` should land early, justify it on the honest ground (`pkg/schema` is a Phase 0 deliverable and A.10's fields are already normative) and then land only A.10's fields verbatim (strategy, exploration_constant, probe_budget_pct, max_mcts_depth, escalation_ladder, utility.{4}, observe.{3}), with the invented fields deferred to Phase 4 where their design is actually settled.

### P10 [medium] 'Docker bridge-network hard ceiling: 30 total' is not a hard ceiling, and clamping W on it encodes a host accident into the architecture. I checked: `docker system info --format '{{json .DefaultAddressPools}}'` returns null on this host, i.e. no pools are configured and the daemon is on its 172.16.0.0/12 default.

**Why it breaks:** `default-address-pools` in daemon.json is a documented one-line knob that raises the count arbitrarily (e.g. adding a 10.100.0.0/12 size-24 pool yields thousands). More fundamentally, W concurrent worlds do not require W newly-created networks: a compose project can be pointed at a pre-existing external network, so the harness can pre-allocate a fixed pool of N networks once and recycle them across worlds. The clamp `W <= floor(freeNetworks/2)` = 12 is non-binding on this host anyway (the CPU term gives 4), so the finding drives a Phase 0 delta with no effect on the answer while asserting a false invariant that a later reader will build on.

**Fix:** Restate as an operational precondition, not an architectural ceiling: `thesis doctor` reports free address-pool capacity and tells the user how to raise `default-address-pools` if they want W > 12. Keep the CPU-based clamp (which is the one that actually binds) and drop the network term from the W formula, or reduce it to a startup precondition check.

### P11 [medium] `Reap()` as specified is unsafe and misses the leaks it exists to catch. Specified as: 'Reap() at startup: `docker compose ls --filter name=prothesis- -q` -> `down -v` each.'

**Why it breaks:** I verified `--filter name=` works as a substring match on this host (Compose in Docker 29.1.3), so the command runs, but without `-a` it lists only projects with running containers. The leak that consumes the address pool is a project whose containers exited while its network survived, and those are invisible without `-a`. Second, unconditional reap-at-startup destroys live state: any concurrently running `thesis search` at W=4 has four `prothesis-*` projects up, and CRUCIBLE section H deliberately creates long-lived ones via the global `--no-teardown` flag and `thesis replay WORLD --keep-up`. A second `thesis` invocation would tear down the first one's worlds mid-rollout, surfacing as spurious exit 2 INCONCLUSIVE: the exact failure the reaper was added to prevent.

**Fix:** `docker compose ls -a --filter name=prothesis- -q`, plus a liveness guard: each world writes `.prothesis/runs/<runID>/worker.lock` with its PID at `Up()`, and Reap() skips any project whose runID has a live lock. Reap only orphans (no live lock, or age > threshold). Never reap projects created with `--no-teardown`/`--keep-up`: tag them in the project label and require an explicit `thesis down --all` to remove them.

### P12 [medium] `LeaseOverlapMs` is offered as 'the discriminating signal' that is '> 0 exactly when the lease bug is exploitable and 0 for a correct implementation', and as 'derivable from logs alone with no instrumentation'. Both halves are wrong for the fixture as specified.

**Why it breaks:** Section 5 gives the leader a 5-second lease; a Raft election completes in roughly one election timeout (hundreds of ms). So `lease_expiry(old) - election_time(new)` is positive on essentially every leader pause, for the same structural reason the role-change criterion it replaces is constant. It discriminates 'this system serves lease-based local reads' from 'it does not', not 'this lease implementation is buggy'. A correctly-implemented lease (revoked on step-down, or quorum-renewed) would show the same overlap and no stale read. Second, `lease_expiry(old_leader)` is an internal variable; recovering it from logs requires the system to log lease grants, which an unmodified third-party system will not. CRUCIBLE section L's 'must work on unmodified systems' therefore cuts against this signal, not for it: the analysis cites L as satisfying it.

**Fix:** Keep RoleChurn (term-change count and time-to-stable-leadership after HEAL), which is genuinely bounded for a correct Raft and genuinely unbounded for a thrashing one, and which is log-derivable without lease instrumentation. Replace LeaseOverlapMs with a purely observable proxy: stale-read rate in the driver history during the window `[resume(old_leader), resume + observed_lease_bound]`, where the bound is inferred rather than read out of the system. That keeps DoD #1 satisfiable from the driver's own error/anomaly series, which is what the section 6.2 reconciliation already relies on.

### P13 [medium] Multiple recommendations fork without choosing, in a document that treats decisiveness as the deliverable.

**Why it breaks:** Section 2.2: 'Affine-normalise ... Alternatively scale C_eff = C * (U_max - U_min). Prefer Thompson sampling', three options, no selection. Section 2.3: parsimony 'depth-normalised (or scaled to ~10% of its reporting weight)'; two different functions, unchosen, and they do not agree numerically. Section 5.2: 'saturate the novelty term ... and/or use SearchUtility()'; 'and/or'. Section 5.5: 'Either extend the config or document that only those four are tunable'. Section 1.6: 'Where host ports are unavoidable, a PortLeaser'; a conditional that, per the first finding above, is the actual case. Each of these lands in DECISIONS.md as an unresolved fork, which is precisely the thing DECISIONS.md is supposed to close.

**Fix:** Pick one per fork and state the losing option as rejected with a reason: (2.2) running min/max affine normalisation, since C_eff scaling changes the exploration constant's meaning run-to-run and breaks comparability across trials in DoD #4; (2.3) depth-normalised, i.e. divide the parsimony term by depth, since a flat 10% weight still biases shallow, just less; (5.2) SearchUtility split as primary with novelty_cap = 3 as secondary; (1.6) ephemeral published ports, PortLeaser unnecessary.

### P14 [medium] The 19.4 s probe cost that produces the headline '427 s = 356% of budget' applies a mandatory 6.0 s QUIESCE to all 22 probe worlds, justified as 'section 5: the leader lease is 5 seconds. You cannot assert convergence before the lease expires.'

**Why it breaks:** Section 5 does state the 5-second lease, but nothing makes QUIESCE lease-length for every probe. Section 4.1 defines QUIESCE as 'wait out the convergence grace window': a per-world timing, and the analysis's own Phase 0 delta #2 argues precisely that PhaseTimings must be 'a first-class, serialized, per-world SETTABLE struct' so 'the Saboteur must be able to shorten DRIVE ... and lengthen QUIESCE past the fixture's 5-second lease'. If QUIESCE is settable per world, then only the probes that can produce a lease-window stale read (leader proc.pause, leader/minority net.partition: roughly 3 of 22) need 6 s; a net.latency(50ms) or io.latency probe does not. At a 2 s QUIESCE for the other 19, the sweep is ~19*15.4 + 3*19.4 = 351 s, not 427 s. The direction of the finding survives; the specific multiplier does not, and 356% is the number that will get quoted.

**Fix:** Make QUIESCE per-probe: `quiesce_ms = max(convergence_grace, lease_bound)` only for probes whose kind/target can implicate a lease (proc.pause and net.partition on leader/minority), `convergence_grace` otherwise. Recompute the sweep cost on that basis and restate the budget-overrun ratio. This also strengthens Phase 0 delta #2, which currently reads as motivated by DRIVE alone.

## Missed by the analysis

- A.5's fallback clause is never addressed: 'If no REINFORCE signal is detected during probing, fall back to the base spec's stochastic corpus mutation for the remaining budget. The Saboteur is an accelerant, not a replacement for baseline coverage.' Combined with A.1's 'All other Phase 4 deliverables (log-template coverage, state-abstraction coverage, corpus management) remain in effect', this means the base mutation loop and the energy-weighted corpus must both still be built. The section 7.1 package layout has no corpus.go, energy.go, or mutate.go, and the Strategy seam has no path for handing control back to the mutation strategy mid-budget. CRUCIBLE section G's pseudocode (corpus/select/mutate/cull, rare-event bias, overlap bias) is normative and unimplemented in the design.
- Virtual-clock anchoring is a genuine Phase 0 format decision and it is absent. History log records absolute `t_ns` (section 4.4), fault windows are `start_ms..end_ms` 'relative to DRIVE start on virtual clock' (section 4.3), and `oracle_input.phases` uses start_ms/end_ms. Nothing in the analysis fixes where the t_ns<->virtual-ms mapping lives or that DRIVE t0 must be recorded in the world artifact. Without it, OBSERVE's windowing, A.5's early termination, every oracle's phase filter, and the section 3.3 epoch grid (K = 8 epochs of driveMS/8) are all unanchored. This is exactly the class of thing the analysis says it is hunting: a Phase 0 format that a Phase 4 feature would otherwise force a change to.
- `profiles.smoke: { budget: 90s, worlds: 3, driver_profile: smoke }` is the inner-loop gate per CRUCIBLE section J ('thesis gate --profile smoke --json (90s, inner loop, runs on save)'). 20% of 3 worlds is 0.6, so the Saboteur gets zero probe worlds at smoke, and `search.strategy: saboteur` is the default. The analysis never asks what the Saboteur does at the profile it will run against most often. This needs a defined degradation (e.g. strategy falls back to the regression corpus plus a single no-fault control below N worlds).
- Rule 2 of the directive ('Normative Schemas are Frozen. Do not invent, alter, or improvise field names or semantics') is never cited or reckoned with, despite the Phase 0 deltas inventing roughly a dozen fields across prothesis.yaml, the world file, and WorldResult. Whether these are permitted extensions or Rule 2 violations is the governing question for every schema delta proposed, and it goes unasked.
- Section 3.3 step 6 defers the constraint filter to `perturber.constraints`, but those are free-text English in the frozen config ('never partition more than minority of kv', 'pg must be reachable during SEED'). There is no grammar, no evaluator, and no Phase assignment for them. The enumeration rule silently assumes a constraint engine that no phase deliverable creates. Either the constraint strings need a normative grammar (a Phase 0 schema question) or the enumeration rule needs to state that it enforces only the numeric budget fields.
- CRUCIBLE section C scopes `thesis doctor` to 'inspects the repo and scores determinism readiness: is the clock injectable, is randomness seeded, are there unsynchronized background threads, are wall-clock timeouts used internally. Outputs a ranked list of changes toward Tier A.' The analysis assigns it host-hygiene duties ('thesis doctor must warn on foreign containers') that are invented scope on a command whose purpose is normatively defined elsewhere. Minor, but it is the same category of drift the analysis flags in others.
- The warm-reuse payoff is understated against the analysis's own cost table. It computes 3.3 s of 29 s = 11% by counting only compose up/down, but its own table charges BOOT 4.0 s ('2.0 s measured compose + ~2 s app boot & first election') and TEARDOWN 1.7 s, i.e. 5.7 s of 28.7 s = 20%, and a warm topology would also skip the app boot and first election. The conclusion (reject, because it breaks I2) is right and does not depend on the number, but the number is wrong by ~2x and is presented as measured.
