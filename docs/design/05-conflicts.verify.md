# 05-conflicts.verify

## Verdict

**NEEDS-REVISION**

## Spec fidelity

The design does NOT rename or drop any normative field name: it correctly preserves the I2 tuple (`seed`, `topology_variant`, `driver_profile`, `fault_schedule`, `phase_timings`), all six builtin oracle names including `no_stuck_op`, and the exit-code numbering. Its Q2 correction of the addendum is verified true: on-disk §4.2 lines 162–168 list six builtins including `no_stuck_op`, so the addendum's "SEVEN / lists five / omits no_stuck_op" is wrong on all three counts. Its environment corrections are also verified: `.git` exists on `master` with zero commits, `docker version` returns server 29.1.3, `go.mod` declares `go 1.27.1`, `core.autocrlf=true`, no `.gitattributes`.

However there IS real drift, and it is applied with an inconsistent standard.

1. ADDS FIELDS TO A FROZEN SCHEMA. Rule 2 reads: "All schemas (`prothesis.yaml`, `prothesis.verdict/v1`, `prothesis.oracle_input/v1`, `prothesis.oracle_output/v1`, history log JSONL, exit codes, and fault grammar) are **normative**. Do not invent, alter, or improvise field names or semantics." `prothesis.yaml` is the FIRST item on that list. D8 states: "Schema gains `oracles.params`, `lifecycle`, node `port`, constraint grammar; all inside the lock projection." That is three invented field names in the most explicitly frozen schema. The document is aware of the rule (Q8 defends itself with "This adds no field names, so rule 2 is respected") yet binds D8 as a DECISION rather than leaving it as an OPEN_QUESTION requiring human sign-off. Two of the three also have non-inventing alternatives it never considers (node `port` is derivable from `harness.file` via compose service inspection; the convergence window could live under the existing `profiles` block).

2. ALTERS `prothesis.oracle_input/v1` SEMANTICS. D13: "All 8 phases emitted; intervals may overlap; `BOOT`/`SEED` negative." The frozen §4.5 example is disjoint, contiguous, sorted and non-negative. No field name changes, but the *semantics* of `phases` do, and rule 2 freezes "field names **or semantics**." Third-party oracles (required to be portable per addendum §L) that map a timestamp to its containing interval will now get two answers during PERTURB∩DRIVE.

3. ALTERS EXIT-CODE SEMANTICS. Exit codes are named in rule 2's frozen list. §4.7 defines `3` as "Budget expired **without coverage progress**"; addendum §I repeats "BUDGET_EXHAUSTED **with no coverage progress**." Q19 proposes: "Exit 0 **only** if `worlds_run == worlds_planned`... Any budget-truncated run without a violation exits 3." That inverts code 3's stated trigger for the most common outcome in the system. Q19 keeps this in OPEN_QUESTIONS (correct) but labels it "a *strengthening*, which rule 4 permits": rule 4 permits not silently relaxing; it does not authorize unilaterally redefining a frozen exit code.

4. EXTENDS `driver.cmd`'s PLACEHOLDER VOCABULARY. D7 adds `{plan_path}` and `{node_addrs}`. The justification ("`driver.cmd` is an opaque template string, and the placeholder vocabulary is nowhere enumerated as frozen") is the strongest of the four and is probably right, but §4.2 does exhibit exactly three placeholders and the change silently redefines what a conforming driver must implement.

5. LEGITIMATE, and worth stating so it is not relitigated: the `.thesis` world-file format is NOT in rule 2's frozen list. Adding `provenance` to `World` and choosing canonical JSON is therefore inside the "behavior specified but implementation open" bucket of rule 3, not drift. Q22(b)'s "self-certifying DoD" complaint is correct and the design is entitled to make that choice.

## Confirmed problems (16)

### P1 [high] D3's `Partition.Inject` sketch does not partition anything. It installs only `iptables -I INPUT -s <peer> -p tcp --dport <RaftPort> -j DROP` in the target's netns.

**Why it breaks:** That rule matches only packets ARRIVING at the target on the Raft listen port; i.e. inbound connection attempts from peers. In Raft the leader is the initiator: it dials followers and sends AppendEntries to the FOLLOWER's RaftPort. Those egress packets are untouched, and the followers' replies return to the leader's ephemeral source port (dport = ephemeral, sport = RaftPort), so they do not match `--dport RaftPort` either. With hashicorp/raft (D6), whose NetworkTransport keeps long-lived pooled connections, the already-established leader->follower streams are unaffected in both directions. Net effect: `net.partition(role:leader)` leaves the leader fully able to heartbeat and replicate, no election occurs, and Q1's own corrected 'easy preset' single-fault schedule produces no stale read. The Phase 2 DoD fails for the same reason Q1 says the spec's schedule fails, and the implementer will conclude the FIXTURE is wrong rather than the injector.

**Fix:** Scope by peer address on BOTH chains and BOTH port directions, and cover established flows: for each peer, `-I INPUT -s <peer> -p tcp --dport <raft> -j DROP`, `-I INPUT -s <peer> -p tcp --sport <raft> -j DROP`, `-I OUTPUT -d <peer> -p tcp --dport <raft> -j DROP`, `-I OUTPUT -d <peer> -p tcp --sport <raft> -j DROP`. Use `-j DROP` (not REJECT) so the fault presents as a black hole rather than a fast failure. Validate the injector against an assertion (peer-to-peer Raft RPC fails AND the client path still succeeds) before ever running the Phase 2 DoD.

### P2 [high] D10's lock projection omits the four config keys an agent would actually edit to weaken the gate: `oracles.builtin`, `driver.profiles`, `perturber.constraints`, and the `harness.nodes` topology.

**Why it breaks:** D10 enumerates the projection as 'allow/deny set, `max_concurrent_faults`, `max_faults_per_world`, per-profile budgets and world counts, `oracles.params`, oracle file digests, regression file list.' 'Oracle file digests' covers external scripts in `oracles.dir`; it does not cover the `oracles.builtin` enable-list. So deleting `no_stuck_op` from `oracles.builtin` (the single cheapest way to make a failing gate pass) leaves the manifest hash unchanged and `thesis gate` returns 0. Likewise `driver.profiles.gate.ops: 20000 -> 10` guts the workload while 'per-profile budgets' (the `profiles:` block) hashes identically; adding a `perturber.constraints` entry narrows the reachable fault space, which addendum §E.2 explicitly classifies as a lock change; and dropping `harness.nodes` from 3 to 1 makes every quorum fault a no-op. This defeats I6 and anti-gaming rules 1 and 2 at precisely the points they exist to defend, and it does so silently.

**Fix:** Define the projection by exclusion, not enumeration: hash the whole canonicalised `prothesis.yaml` MINUS an explicit, short allowlist of gate-irrelevant keys (`name`, `artifacts.*`, comments/formatting). Q23's ergonomic complaint ('renaming a service trips ORACLE_DRIFT') is then handled by the field-level WEAKENING/STRENGTHENING diff D10 already proposes, not by shrinking what is hashed. Add a lock unit test that asserts each of these four edits produces exit 4.

### P3 [high] Q22's recommendation to 'Pin `t_ns` = Unix epoch nanoseconds' is incompatible with the frozen `prothesis.oracle_input/v1`, which expresses `phases` as `start_ms`/`end_ms` relative to DRIVE start and carries no epoch anchor field.

**Why it breaks:** An external oracle receives `history_path` (absolute epoch nanoseconds under this decision) and `phases` (milliseconds relative to DRIVE start). The frozen input object has exactly six keys (`schema`, `history_path`, `final_state_path`, `telemetry_path`, `world_path`, `phases`) none of which conveys the DRIVE-start wall-clock instant. The oracle therefore cannot map any operation to a phase, which defeats I5 phase-aware assertion for every external oracle, including the `linearizable.kv` checker whose op-ID witness is Phase 3's DoD. The only in-band anchor is the `{"type":"info","event":"phase"}` marker line, which §4.4 exhibits only for HEAL and which the design never commits to emitting for DRIVE. Separately, Q22's diagnosis of the §4.4 sample is wrong: `1725300000000000` is not '20 days after the epoch or three digits lost' ambiguously; it is exactly Unix MICROseconds for 2024-09-02, so the sample is a µs value in a `t_ns` field. Choosing absolute-epoch on the strength of a misread makes the harder choice.

**Fix:** Pin `t_ns` to nanoseconds since DRIVE start (which also matches Jepsen/Elle convention, per §4.4's own 'compatible with Jepsen/Elle models'), so history and `phases` share one epoch and no new field is needed in the frozen input schema. If absolute epoch is kept instead, the harness MUST guarantee a DRIVE phase-marker line as the first record of every history and that guarantee must be normative in Phase 0, not implied.

### P4 [high] Nothing in the design names the Compose project, and nothing persists the state that `thesis down` needs. `thesis up && thesis down` are two separate OS processes.

**Why it breaks:** Phase 0 DoD (a) is exactly these two commands. `docker compose -f <file> down -v` derives its project name from the compose file's parent directory, so: (i) two concurrent worlds from the same fixture collide on container names and on `-v` volume removal, and Q21 commitment #2 (ephemeral ports for Phase 4 parallelism) is necessary but nowhere near sufficient; project namespacing is the actual mechanism; (ii) `thesis down` cannot know which world it is tearing down, nor which resolved ephemeral ports D5 discovered during `up`, because that state died with the `up` process; (iii) a stale project left by `--no-teardown` (an addendum §H global flag) is unreachable for later cleanup. The design's own measured 7.19 s cycle was a single sequential project, so the measurement does not exercise this at all.

**Fix:** Phase 0 must decide and record: a per-world project name (`thesis-<run_id>-<world_id>`) passed as `docker compose -p`, and a `.prothesis/state/<project>.json` written by `up` holding the project name, compose file digest, resolved `{host}:{port}` map and PIDs. `down` reads it, tears down by project, and is idempotent when the file or project is already gone. Add `--remove-orphans`. Add this as a ninth Q21 forward commitment; it is cheap now and blocks Phase 4 if deferred.

### P5 [high] The design says nothing about PRNG stream architecture, despite `internal/recorder` 'deterministic PRNG seed streams' being a named Phase 0 deliverable and `seed` being the first element of the I2 world tuple.

**Why it breaks:** This is the classic delta-debugging/PRNG interaction and it is a Phase 0 decision that silently forecloses Phase 5. If fault timings, target selection and workload parameters are all drawn sequentially from one source seeded with `seed`, then `ddmin` removing fault #3 shifts every subsequent draw, so the shrunk world's *remaining* faults land on different nodes at different times and the violation vanishes: ddmin will then discard faults that were in fact essential, and the 3/3 confirmation gate will fail nondeterministically in a way indistinguishable from Tier B flakiness. There is also an unaddressed Go hazard: `math/rand`'s global functions are randomly auto-seeded since Go 1.20 and `rand.Seed` is deprecated, while `math/rand/v2` (available at the stated Go 1.22 floor) has no global seeding at all and no `Seed` function, so 'seeded randomness' has to be an explicit `*rand.Rand` threaded through the recorder, and the higher-level helpers (`Shuffle`, `Perm`, `IntN`) carry no cross-release sequence-stability guarantee for committed regression worlds.

**Fix:** Decide in Phase 0: independent named streams derived by domain separation, e.g. `stream(name) = rand.New(rand.NewPCG(splitmix(seed, fnv64(name)), ...))` with names `faults`, `targets`, `windows`, `workload`, `client_sched`. Each fault draws from a stream keyed by its own stable identity, so removing one fault cannot perturb another. Explicitly forbid the package-level `math/rand` functions in `internal/`, and pin the generator (PCG) plus the derivation function so committed `.thesis` files stay replayable across Go releases.

### P6 [high] The D1 codec sketch contains an internal contradiction and an unsolved type problem: Q22 defines canonical `.thesis` as having 'lexicographically sorted keys', but the implementation emits struct fields in declaration order, and the comment asserts 'no map may appear in this type graph' when the fault grammar requires heterogeneous parameters.

**Why it breaks:** Go's `encoding/json` sorts MAP keys but emits STRUCT fields in declaration order, so `World` serialises as schema, seed, topology_variant, driver_profile, fault_schedule, phase_timings, provenance, not lexicographic. The written spec and the written code disagree, and whichever a second implementation follows (a Python analysis tool, or the external oracle reading `world_path`) will produce non-byte-identical output, which is the one thing Phase 0 DoD (b) exists to prevent. Separately, §4.3 requires `net.latency(mean,jitter)`, `net.loss(pct)`, `net.bandwidth(bps)`, `proc.kill(signal)`, `io.error(rate)`: heterogeneous per-kind parameters. `Fault` is left undefined in the sketch, and the obvious `map[string]any` reintroduces exactly the float64 coercion Q22(c) was written to prevent.

**Fix:** Drop 'lexicographically sorted keys' from the canonical-form definition and state 'struct declaration order; no Go maps anywhere in the type graph'; declaration order is deterministic and is what the encoder actually does. Then make `Fault.Params` a typed per-kind struct selected on `Kind` (custom `UnmarshalJSON` dispatching on the kind field), or, if a generic bag is unavoidable, `map[string]json.Number` so integer fidelity survives. Write the golden-file test against the real `Fault` type, not against a `World` with an empty `fault_schedule`.

### P7 [medium] Q3's remedy for `clock.skew`/`clock.jump`: an env var `THESIS_CLOCK_OFFSET_MS` read through the fixture's clock abstraction; cannot satisfy the Phase 2 DoD even against the cooperating fixture.

**Why it breaks:** The Phase 2 DoD is 'Every fault kind can be injected and cleanly withdrawn,' and §4.3 gives every fault a `@start_ms..end_ms` window on the virtual clock. An environment variable is read once at process start: it cannot be injected at t=8000 nor withdrawn at t=14000, and changing it requires a restart, which is a different fault (`proc.restart`) with different observable consequences. So after correctly diagnosing that libfaketime and time namespaces are dead ends (that analysis is right: `CGO_ENABLED=0` has no `ld.so`, Go's `nanotime` calls the vDSO directly bypassing libc interposition, `CLONE_NEWTIME` offsets only `CLOCK_MONOTONIC`/`CLOCK_BOOTTIME`, and Docker does not plumb it), the design lands on a remedy that still leaves `clock.*` unwindowable. Q21 commitment #5 ('injectable clock behind an interface') is therefore underspecified in the direction that matters.

**Fix:** Make the fixture's clock RUNTIME-settable, not boot-settable: a small admin endpoint (`POST /debug/clock {offset_ms}`) or a control file the clock abstraction re-reads, so inject and withdraw are both real operations on a running process. Restate Q21 commitment #5 as 'runtime-settable clock offset with an inject/withdraw control surface'. Keep D12's UNSUPPORTED path for unmodified SUTs.

### P8 [medium] D12 ('unsupported fault -> exit 2 INCONCLUSIVE') specifies a per-fault outcome but never specifies aggregation across faults, worlds, or a run, and it collides with the addendum's agent-loop contract.

**Why it breaks:** Addendum §I binds code 2 to 'retry once, then escalate to human.' An unsupported fault kind is deterministic, not transient: the retry always fails and every run escalates. Worse, the aggregation is undefined at three levels. Does one unsupported fault fail its world, or the whole run? Under Phase 4, addendum §G seeds the corpus with 'one world per allowed fault kind', and the scaffolded config ships `clock.skew` in `allow:`, so a search against any non-cooperating SUT seeds a guaranteed-inconclusive world, and any mutation that introduces an unsupported kind can terminate an 8-hour search with exit 2. Removing the kind from `allow:` to escape is explicitly a lock weakening under anti-gaming rule 2, so the agent has no legal exit. Related: 'recorded in the world file' makes a `.thesis` carry a platform-specific capability result, which contradicts addendum §L portability; a world discovered on Linux would replay as recorded-inconclusive on this Windows host.

**Fix:** Separate the levels. A fault kind unsupported by the (backend, platform) pair is a CONFIG/capability fact discovered at PLAN time, not run time: `thesis doctor` and config validation report it, the run refuses to start with exit 5 and a message naming the offending `allow:` entry and the missing capability, and the lock records the platform capability set so narrowing `allow:` on one platform cannot be laundered as a fix. Reserve exit 2 for genuinely transient harness failures. Never write platform capability results into a `.thesis`.

### P9 [medium] D6 ('fixture built on hashicorp/raft + raft-boltdb, lease bug authored on top') collides with hashicorp/raft's config validation if the 5-second read lease is wired to raft's own lease timer.

**Why it breaks:** `ValidateConfig` enforces `LeaderLeaseTimeout <= HeartbeatTimeout` and `ElectionTimeout >= HeartbeatTimeout`. The fixture bug requires the OLD leader's read lease to still be valid when the NEW leader has already been elected and has committed a write: i.e. lease_duration must exceed election latency. Chaining the two constraints gives lease <= heartbeat <= election, the exact opposite. An implementer who sets `LeaderLeaseTimeout: 5s` gets a rejected config, or, on raising `HeartbeatTimeout` to 6s to satisfy it, gets elections that cannot complete until well after the 5s lease has expired: the anomaly window closes and the fixture cannot exhibit the bug it exists to exhibit. This is the crux of the entire project and D6 states it in one line with no timing analysis. D6 also sits awkwardly against the briefing's 'minimize third-party dependencies' (raft + raft-boltdb pulls go-hclog, go-msgpack, armon/go-metrics, bbolt).

**Fix:** State explicitly in D6 that the 5-second read lease is an APPLICATION-level lease in the KV read path, tracked independently of `raft.Config.LeaderLeaseTimeout`, gated on `r.State() == Leader` and a locally-stored lease deadline that is deliberately not revalidated against `VerifyLeader()`. Set raft's own timers fast (HeartbeatTimeout ~500ms, ElectionTimeout ~1s) so a new leader is elected and commits well inside the stale 5s app lease. Record the timing budget (election latency < app lease < fault duration) as the fixture's design contract, since Q1, Q7's difficulty knob and the Phase 2 DoD all depend on it.

### P10 [medium] Q17's remedy: 'Partition histories by key before checking; a per-key register model is the right abstraction'; is unsound for the frozen `profiles.gate` workload, which is `mix: { read: 0.4, write: 0.4, txn: 0.2 }`.

**Why it breaks:** Per-key partitioning is only sound when every operation touches exactly one key. A multi-key transaction spans partitions; checking each partition's projection independently accepts histories that admit no single serial order over the whole transaction set, so real violations pass. This is a FALSE PASS in the consistency checker: the most dangerous class of error in this system, and precisely the failure mode Q17's own point (c) argues against for timeouts. The design correctly refuses to map checker timeouts to PASS but then introduces a different silent-PASS path one paragraph earlier. `admin` ops in the `soak` mix have the same problem and are never defined at all.

**Fix:** Either define the fixture's `txn` as single-key (a compare-and-set on one key), record that in DECISIONS.md, and gate per-key partitioning on a validated 'all ops single-key' precondition that hard-errors when violated; or keep multi-key txns and use a transactional checker (Elle list-append / rw-register) on the unpartitioned history with the timeout/memory ceiling and INCONCLUSIVE mapping Q17 already specifies. Do not let partitioning be applied to a history it has not been proven sound for. Op semantics for `txn` and `admin` are a Phase 0 loadgen commitment and belong on the Q21 list.

### P11 [medium] Nothing specifies who writes the `{"type":"info","event":"phase","phase":"..."}` marker lines into the history file, which `driver.cmd` owns via `{history_path}`.

**Why it breaks:** §4.4's sample shows a phase marker interleaved in the same JSONL stream as the driver's op records, but §4.2 hands `{history_path}` to an external driver process. Two processes appending to one file gives torn lines under concurrent writes (POSIX O_APPEND atomicity holds only up to PIPE_BUF-ish sizes and is not guaranteed across the Docker Desktop VM/9p or Windows bind-mount boundary this project actually runs on), and a torn line makes the whole history unparseable: presenting as a spurious INCONCLUSIVE that will read as an environment flake. This is a Phase 0/1 recorder-driver contract question, it is what makes phase-aware assertion (I5) possible at all, and the design's codec section never touches the history writer.

**Fix:** Decide in Phase 0: the driver writes ONLY op records to `{history_path}`; the harness writes phase markers to a separate `phases.jsonl` and the recorder merges them by timestamp into the canonical history at TEARDOWN, emitting one file for the oracle contract. Alternative if a single live stream is wanted: the driver writes to a pipe the harness owns and the harness is the sole writer to disk. Either way state it normatively, because the external oracle contract depends on the merged file existing.

### P12 [medium] Q8's justification for changing the frozen `phases` semantics overstates the problem: 'an oracle cannot say "I am invalid during PERTURB" if PERTURB is not in the input.'

**Why it breaks:** `prothesis.oracle_output/v1` carries `valid_phases` as a DECLARATION by the oracle; the harness, which knows all eight phases, does the filtering, and §6 Phase 3 lists 'Phase-validity checks' as a harness deliverable, not an oracle one. So an oracle can declare `valid_phases: ["ASSERT"]` and be correctly excluded during PERTURB with no change to the input array. Furthermore `prothesis.oracle_input/v1` already supplies `world_path`, and the `.thesis` world contains `fault_schedule`, so the perturbation windows are already reachable by any oracle that wants them. The design therefore alters a frozen schema's semantics (breaking third-party oracles that assume disjoint, sorted, non-negative intervals) to solve a problem the frozen schema already solves.

**Fix:** Keep `phases` disjoint, sorted and non-negative as exemplified. Emit BOOT and SEED as non-negative windows preceding DRIVE if a full lifecycle view is wanted, and express PERTURB through `world_path`'s `fault_schedule`, which is where it already lives. If overlapping phases are genuinely needed later, that is a `prothesis.oracle_input/v2` conversation, not a v1 reinterpretation.

### P13 [medium] `VerifyResidual` is specified as asserting `iptables -S INPUT` 'contains no thesis-owned rules', but the injected rules carry no ownership marker.

**Why it breaks:** The rules as written in D3 are indistinguishable from any rule the SUT image installed itself. Under addendum §L ('must work on unmodified systems') the target container may legitimately ship its own filter rules, so the check as stated is either unimplementable or will produce a false HEAL failure on any SUT that uses iptables. §4.3's Critical Guarantee ('HEAL must verify that no residual network rules... persist') is then unmet, which in turn means a leaked DROP rule silently poisons the NEXT world on a reused container.

**Fix:** Tag every injected rule with `-m comment --comment "thesis:<run_id>:<fault_id>"` and make residual verification a grep for the `thesis:` prefix; withdraw by comment match rather than by `-D` of a reconstructed rule spec (which fails if the rule was already partially removed). Do the same for tc: record the qdisc handle range thesis owns. Also snapshot `iptables-save` and `tc qdisc show` at BOOT so HEAL compares against the observed baseline, not against an assumed-empty one.

### P14 [medium] The audit's on-disk inventory is incomplete in a way that matters: `C:\AI Projects\Pro-synthesis\SABOTEUR_INJECTION.md` exists on disk and opens with 'This addendum supersedes the coverage-guided mutation loop described in Phase 4 Section 6 of the base specification', introduces a new top-level subsystem, an MCTS/UCT search, and a 'normative' utility function with fixed constants. The design never mentions it.

**Why it breaks:** The design's central methodological claim is that it verified on-disk content and caught the addendum lying about it (Q2), and it presents a table of what is on disk. Omitting a file that explicitly asserts authority over a phase of the base spec undercuts that claim and leaves the exact conflict this document exists to catalogue unrecorded. Concretely: either that file is normative, in which case Phase 4's deliverables and the design's Q7 benchmark analysis are aimed at the wrong search algorithm; or it is not normative, in which case a future implementing agent that reads the repo without this briefing will implement it. Silence produces the second outcome by default. Note also that `cmd/`, `internal/`, `pkg/`, `testdata/` and `docs/` are EMPTY directories, not 'scaffolded' as the table implies.

**Fix:** Add an OPEN_QUESTIONS entry naming `SABOTEUR_INJECTION.md`, stating that the normative set for this build is exactly `PRO_THESIS_FABLE_PROMPT.md` plus the pasted CRUCIBLE content, that the file is treated as non-normative pending explicit human confirmation, and that no Phase 4 work may consume it until then. Content that arrives on disk claiming to supersede a frozen spec is a conflict under rule 4 by definition and must be escalated, not ignored.

### P15 [low] Q11's proposed `.gitattributes` marks `*.thesis` and `.prothesis/lock` as `binary`, which defeats the human review that anti-gaming rules 1 and 4 depend on.

**Why it breaks:** `binary` implies `-text -diff`. Addendum §E.1 requires a lock bump to be 'a separate, human-reviewed commit', and §E.4 makes any change to the regression corpus a lock change: both reviews are performed by reading a diff. Marking these files binary makes every such diff render as 'Binary files differ', so the reviewer sees that something changed but not what, which is exactly the state an adversarial agent benefits from. The CRLF protection Q11 correctly identifies does not require `binary`.

**Fix:** Use `*.thesis text eol=lf` and `.prothesis/lock text eol=lf`. Both guarantee LF in the repo and on checkout on Windows (preserving byte-identity and the SHA-256 manifest) while keeping diffs readable. Reserve `binary` for genuine binaries. The rest of Q11's diagnosis is correct and verified on this machine: `core.autocrlf=true`, no `.gitattributes` present.

### P16 [low] Q7's Fisher's exact p-values are two-sided values presented as one-sided.

**Why it breaks:** For a 2x2 table of 9/10 vs 2/10 the one-sided Fisher p is 0.0027, not the stated 0.0055; for 10/10 vs 0/10 it is 5.4e-6, not 1.1e-5. Both quoted figures are the two-sided values. The conclusion (Fisher's exact is adequately powered at n=10 and handles the right-censoring that invalidates a mean/median comparison) survives and is correct, but a pre-registered benchmark protocol that states its test and its numbers wrongly will be re-derived by whoever implements it, and a factor-of-two error in a pre-registration is the kind of thing that later looks like the analysis was tuned to the result. The companion Mann-Whitney claim (U <= 23 at two-tailed alpha=0.05, n1=n2=10) is correct.

**Fix:** Restate as: one-sided Fisher's exact, 9/10 vs 2/10 -> p = 0.0027; 10/10 vs 0/10 -> p = 5.4e-6. Pre-register the direction, the alpha, the world budget per arm, and the difficulty preset before the search loop is written, exactly as Q7 recommends.

## Missing

- Oracle enum sets are absent from the design even though `pkg/schema` ('Go types for all normative schemas') is a Phase 0 deliverable. The addendum's eight oracle classes (`crash`, `consistency`, `liveness`, `convergence`, `resource`, `safety`, `differential`, `metamorphic`), the `status` values implied by §4.5's exit codes (ok / violated / inconclusive), the `severity` values, and the top-level `verdict` values (PASS/FAIL) are all normative vocabulary that Phase 0 must freeze as Go types. D8 lists four schema additions and none of these.
- Quorum target resolution against an unmodified SUT is never treated as a conflict. §6 Phase 2 mandates a 'Quorum target resolver (`role:leader`, `minority(kv)`, `majority(kv)`)' and §4.4/Phase 4 mandate state-abstraction coverage over `(role, term, bucketed_queue_depth, connection_count)`. Determining which node is leader, and its term, is impossible for an arbitrary unmodified system: the identical §L instrumentation conflict Q18 correctly raises for `no_unbounded_queue` and `resource_return_to_baseline`, applied to a mandatory Phase 2 deliverable and the primary Phase 4 coverage signal. It needs the same tiered/opt-in treatment and the same honest degradation, and it needs a Phase 0 decision about where role/term come from for the fixture.
- The `process` backend is never mentioned. §1.6 makes it one of two v1 backends and D11's validator explicitly ACCEPTS `backend: process`, but the briefing states a process backend on Windows cannot do `proc.pause` or `net.partition` at all. Accepting the value while every fault kind is unsupported gives a config that validates and then fails at run time: the D12 trap, on the default platform. Phase 0 should decide whether `process` is rejected on Windows, or accepted fault-free.
- `thesis init` is a named Phase 0 CLI deliverable and its output is never specified: which `prothesis.yaml` it writes (the six builtins, `clock.skew` in `allow:`, `io.fill` in `deny:` per Q4), whether it creates `.prothesis/oracles/` and `.prothesis/regressions/`, whether it writes `.gitattributes` (Q11 says 'first commit' but never says which command produces it), and whether re-running it is idempotent or refuses to overwrite.
- The relationship between Compose healthchecks and `harness.health` probes is undecided. The design's own timing measurement used `up --wait` (Compose healthcheck-gated) while §4.1 BOOT specifies polling `harness.health` probes. Two competing readiness mechanisms with different timeouts (`health.timeout: 30s` vs the healthcheck's own retries) will disagree, and BOOT's completion instant is the anchor for the entire virtual clock.
- Artifact retention (`artifacts.retain_passing: 3`, `retain_failing: all`) has no owner. It is in the frozen config, it governs `.prothesis/runs/` which `.gitignore` already excludes, and pruning interacts with `thesis report RUN_ID`, but no phase claims it and Phase 0 creates the directory layout it operates on.
- `{node_addrs}` is introduced in D7 as a driver placeholder but never given a format. Since it is being frozen in Phase 0 alongside `{plan_path}`, its encoding (JSON object? comma-separated `id=host:port`? a file path?) must be pinned now for the same reason the rest of the vocabulary is.
- Op-shrinking's applicability limit is unstated. `{plan_path}` requires the DRIVER to implement plan replay; for any third-party loadgen against an unmodified system it will not, so Phase 5's ddmin-over-ops is a fixture-and-cooperating-drivers-only capability. The design presents it as general. It needs the same explicit 'not attempted, with reason' verdict path that Q6 correctly demands for skipped shrinking.
